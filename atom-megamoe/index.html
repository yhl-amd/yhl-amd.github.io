第一部分

概览：MegaMoE 是什么

四张图建立直觉。

1.1一层 MoE 要做什么

token 要去 expert 所在的卡上算，算完再回来。

要点
  • V4-Pro：384 个 expert，每个 token 选 6 个
  • 8 卡 EP，每卡放 48 个 expert
  • 8 张卡的 token 同时这样走，① 和 ③ 是全员对全员的数据交换

1.2问题出在等待

一步做完才做下一步，通信和计算总有一个闲着。

要点
  • 传统做法：每一步都要等所有卡做完
  • decode 时每个 expert 只有几十行，GEMM 很快，等待占比更大

1.3MegaMoE 的三个思路

打个比方流水线：零件到一箱就开工，成品直接投进客户的信箱。

1.4在 ATOM 里：谁负责什么

开关是 --moe-backend mega（DP-attention + EP8，MI355X）。

  1. MegaMoE 把一整层 MoE 的通信和计算揉在一起做，边传边算。
  2. ATOM 只算路由并交出去，真正的工作在 aiter 的 4 个 kernel 里。
  3. 数据直接写进对方显存，再用计数器通知对方。

A · 数据怎么走

2.14 次 launch 各做什么

一层 MoE = 同一条 stream 上的 4 次 launch。

要点
  • 每张卡同时是 s（token 的主人）和 d（expert 的主人），图里拆开画
  • L2 里推数据和 GEMM1 同时进行；L3 里 GEMM2 和写回同时进行
  • combine 只读本地：结果早已被别的卡写进来了

2.2一个 token 的旅程

rank 0 的 token 17，选中 expert 5、60、61、200、201、383。

要点
  • 发出去的每一行带着 srcmap："我来自 rank 0 的 token 17、slot 2"
  • GEMM2 算完乘上 w，按 srcmap 写回 rank 0 的第 17 × 6 + slot 行
  • 每一行只有一个写者，不需要原子操作

这块内存是谁的

这些 buffer 是谁的？每张卡一份，在自己的 HBM 里；"共享"指别的卡能直接往里写。

要点
  • 接收区、结果区都是每卡一份、布局一致（对称堆），不是 8 张卡合用一块
  • 显存按"每张卡"算：大实例约 10.6 GB，是每张卡都要占的
  • 8 张卡会同时往同一张卡的接收区写，所以必须约定好"谁写哪几行"：这就是 2.6 的两种 dispatch

2.4怎么知道数据到了：计数器

写完一段就给对方 +1，加到期望值就开算。

要点
  • 期望值在 L1 规划布局时就算好了：几段数据覆盖这个 tile，就是几
  • 先 fence 再 +1，保证数据比计数先可见
  • 计数器只增不清零，每次调用期望值往上加，免去复位，graph 重放也不用 CPU 插手
B · 接收区怎么排、实例怎么选

2.5容量 mtpr

mtpr = 一个实例单次调用时，每张卡最多能放进来的 token 数。

要点
  • 所有 buffer 按 mtpr 在构造时一次分配好（CUDA graph、对称内存都需要）
  • mtpr 决定 dispatch 方式和回传格式 → 同一步里全组必须用同一个实例
  • 它是上限：实际行数 ≤ mtpr 即可，tile 大小按实际行数挑

2.6接收区怎么排：fixed-slot 与 compact

2.3 说过：每张卡有自己的接收区，8 张卡同时往里写。这一节回答：接收区里面怎么排。

①接收区里，一个 expert 一段

接收区里一个 expert 占一段：段里就是这一步要送进这个 expert 做 GEMM 的 token 行。

要点
  • "expert 12 的段"= rank 1 接收区里一段连续的行，装着这一步所有要进 expert 12 GEMM 的 token
  • 每一行是一个 (token, slot)：一个 token 如果选了 rank 1 上的两个 expert，会在两段里各出现一次
  • 段长就是这个 expert 本步 GEMM 的 M，补齐到 tile 高度，保证一个 tile 不跨 expert

②两种排法

问题：每个 expert 这一步收多少行事先不知道，接收区里该怎么排？两种模式给了两种答案：

③fixed-slot 里，一行是谁的、结果还回哪

注意：fixed-slot 固定的是"每个 expert 一块"，块里面不按 rank 分，谁先到谁拿前面的行。

要点
  • fixed-slot 里同一个 expert 的行来自不同 rank、按到达顺序交错排列，所以每一行都得自带 srcmap（见下图）
  • 不按 rank 预分，是为了让行挤在区域开头，tile 是满的；按 rank 分虽然省掉取号，但行太零散
  • 到达顺序每次可能不同，不影响结果：每行独立计算，再靠 srcmap 写回固定位置

fixed-slot 不交换计数，那怎么知道一行是谁的、结果还回哪？每一行都挂着一张"标签"（srcmap），像快递单上的寄件人地址。

要点
  • 每一行都挂着标签：srcmap 写明从哪来、回哪去，wts 是路由权重，和数据写在同一个行号
  • 去程要协调（8 张卡抢同一块地方）；回程不用（每个 token 的 6 个结果位置是固定的，只有一个写者）
  • rank 1 怎么知道一共几行：收齐 8 个 COUNT_DONE 后读 RUNNING[e]；补齐的空行标签是哨兵值，算完直接丢弃

④预留多少显存

两种预留方式：按"每个 expert 的最坏情况"，还是按"整张卡的最坏情况"。

mtprfixed-slot 预留compact 预留
128≈ 354 MB≈ 90 MB
4096≈ 11.3 GB≈ 1.46 GB
16384≈ 45 GB，放不下≈ 5.68 GB
要点
  • fixed-slot 让每个 expert 单独扛最坏情况，compact 只扛整卡的最坏情况：差 48 ÷ 6 = 8 倍
  • mtpr = 128 时 compact 反而更省（90 MB 对 354 MB）
  • 所以 decode 选 fixed-slot 不是为了省显存，是为了省掉一次跨卡计数交换的延迟
  • compact 预留的空间，均匀路由时平均只用到约 1/8，但必须按最坏情况留
  • 多卡同时写也不撞车：fixed-slot 靠原子取号错开，compact 靠事先算好的偏移错开

2.7compact 的 L1 prepare：为什么要交换计数

L1 是开工前的准备：先把 token 量化好，再和所有卡对一遍账，算清谁给谁发多少行、各自写到哪。

①为什么要交换计数

L1 最核心的一步是交换计数。原因：8 张卡同时往同一个接收区写，不知道别人发多少，就定不下自己写到哪。

交换计数是为了定下三件事
  • 起点（发送方用）：我写在 expert 段里的第几行，要先知道排在我前面的卡发了多少
  • 段长（接收方用）：每个 expert 收多少行，下一个 expert 才知道从哪开始，才能紧凑排
  • tile 期望值（接收方用）：每个 tile 由几段数据填满，才能"凑齐就开算"（2.4）

fixed-slot 不交换计数，用的是另一种办法：每个 expert 按最坏情况留 1024 行，发送方原子取号。代价是显存，而且只能等所有卡发完才开算（2.6）。

②为什么是全员交换整张表

为什么是"全员交换整张表"，而不是只把计数告诉接收方？

③这张表怎么用

这张表怎么用？先缩小来看：只画 4 张卡，只看 rank 1 上的两个 expert（e12、e13）。

  1. 每张卡数自己的rank 2 数出"我给 e12 发 3 行、给 e13 发 0 行"，这就是表里 rank 2 那一行。它只知道自己这一行。
  2. 交换每张卡把自己那一行发给所有卡，之后人手一张完整的表。
  3. 接收方看整列rank 1 把 e12 那一列加起来是 6 行，补齐到 32 行，于是 e13 的段从第 32 行开始。
  4. 发送方看自己上面的格子rank 2 在 e12 列里，上面是 rank 0 的 2 和 rank 1 的 0，加起来是 2，所以它写 e12 段的第 2、3、4 行。

大家用的是同一张表、同一种加法，算出的位置自然一致，所以谁也不用问谁。真实的表是 8 行 × 392 列：8 张卡 × 48 个 expert = 384 列，再加 8 个 fanout 组段（2.6 的去重机制，这里可以先忽略）。

④L1 里谁来做

L1 里谁来做这些事：一次 launch，三种角色。

fixed-slot 的 L1compact 的 L1（prepare）
做什么只量化（per_1x32_mx_quant）量化 + 数路由 + 交换计数 + 规划
跨卡通信无计数表 all-gather、PLAN_READY
写到哪一行留到 L2 原子取号在 L1 就算好
要点
  • 一次 launch 三种角色：quant CTA 量化完就退出，group CTA 数路由，owner 负责对账和规划
  • 这次交换是一层 MoE 里第一个跨卡屏障；decode 用 fixed-slot，省掉的就是它
  • 单独成一个 kernel，是为了不占 GEMM1 需要的大块 LDS；owner 还顺带用这张表选出下一轮的 fanout pair

2.8每一步用哪个实例：decode、MTP、prefill

C · ATOM 侧与优化

2.9ATOM 侧做了什么

交出路由

只交 topk_ids + topk_weights，hash 路由层也一样。

ids = [5, 60, 61, 200, 201, 383]，weights = [.31, .22, .15, .12, .11, .09]

shared expert 单独算

V4-Pro：shared 是 FP8，routed 是 FP4，不融合；在另一条 stream 上并行，最后相加。

MegaMoE 只看到 384 个 routed expert，每卡 48 个

大小两个实例

prefill 用大实例（compact），decode 用小实例（fixed-slot），见 2.5、2.8。

全组 decode、每卡 64 行 → 小实例；有一张卡在 prefill → 全组大实例

补齐行置 -1

ATOM_MEGA_MASK_PAD_ROWS=1：补齐出来的假 token 不发送、不计算，combine 返回 0。

真实 40 行、对齐到 64 行 → 第 40–63 行 id 改成 -1。为什么要做见 2.10

2.10DP pad 行屏蔽（ATOM #2463）

DP-attention 下每张卡都要补齐到同样的行数，补出来的"假 token"原本也会走完整个 MoE，而且会全部挤到同几个 expert 上。

已做 · 已合入 main（2026-10-05）

ATOM #2463 + 配套 aiter #6127。开关 ATOM_MEGA_MASK_PAD_ROWS=1（默认关）。验证与待补的吞吐数据见 3.14。

难点#2463 的做法
graph 重放时不跑 Python，怎么知道这一步哪些是 pad 行mask 在 device 上算，用每步都会刷新的持久 buffer：target pass 取 cu_seqlens_q[running_bs]（补出来的请求长度为 0，所以这就是真实 token 数）；draft pass 用 target 记下的真实请求数 × q
combine 默认把 6 个 slot 全加起来，-1 slot 里是旧数据aiter 配套 PR（ROCm/aiter#6127）让 combine 跳过 -1；旧 aiter 则在 op 之后补一次 where(pad, 0, out)
mask 检查本身有开销（约占 prefill 一个 MoE 层的 10%）只在这一步确实有 pad 行时才请求 mask_invalid_slots
别的行集合不能误伤只处理行数正好等于 running_tokens 的 pass；TBO micro-batch、PCP 分片、plugin 前端都不启用
要点
  • 省的是两样：pad 行本身的 dispatch / GEMM / combine；以及它们挤到同几个 expert 造成的热点（这一步要等最慢的那张卡）
  • 开关是 ATOM_MEGA_MASK_PAD_ROWS=1（默认关）。aiter 永远不计数、不发送、不计算 id < 0 的路由，而且跨卡握手和路由计数无关，所以整行甚至整张卡全是 -1 也不会卡死
  • 同一个 PR 的另一半是可调的 decode 小实例容量 ATOM_MEGA_DECODE_MTPR（2.8）：开 MTP 后 decode 图有 336 / 896 行，超过 128 就会退回大实例
  • PR 里的验证：DeepSeek-V4-Pro DSpark DEP 跑 3600 s agentic replay 零错误；同一容器 mask 开 / 关 GSM8K 5-shot 0.9545 / 0.9469（strict），DSpark 接受率 56.69% / 56.99%，精度不受影响。PR 描述里没有贴吞吐数字

①重叠发生在哪

②为什么是 4 个 kernel

为什么 DeepSeek 只要 1 个 kernel，aiter 却拆成 4 个？两边的根本区别在于：不同阶段要的资源不一样，DeepGEMM 在一个 CTA 内按 warp 分角色来解决，aiter 则拆成多个 kernel、每个各定形状。

要解决的问题DeepGEMM（1 个 kernel）aiter（4 次 launch）
通信和计算同时跑同一个 CTA 里 dispatch warp 和 MMA warp 分工stage1 里 producer CTA 和 consumer CTA 分工
GEMM2 要等 GEMM1L1 每完成一个 N 块就翻一位，L2 按 K 块逐个等；调度器先发几波 L1，防止 L2 占满 CTA 却等不到 L1（死锁）kernel 边界：GEMM1 全部完成才开始 GEMM2
各阶段要的资源不同按 warp 角色调整寄存器（dispatch 48–96，epilogue 168–208）；累加器放 TMEM，不占寄存器每个 kernel 单独定 wave 数、tile 和 LDS；prepare 单独成 kernel 就是为了不占 GEMM1 的 LDS
跨卡同步kernel 内 nvlink_barrier / grid_syncprepare 的计数交换、combine 的跨卡 barrier
输入量化不在 kernel 里：调用前把 fp8 输入拷进 buffer（README："You may fuse these into previous kernels"）在 L1（prepare 的 quant CTA，或 fixed-slot 的独立量化 kernel）
dispatch 方式pull：从远端拉push：写到远端
shared expert在同一个 kernel 里（SharedLinear1/2 任务）不在 MegaMoE 里，另一条 stream 并行（2.9）
要点
  • DeepGEMM 能做成一个 kernel，靠的是 Blackwell 的几样特性：按 warp 角色调整寄存器、累加器放 TMEM、TMA 异步搬运。所以通信、搬运、MMA、epilogue 能在同一个 CTA 里共存而不互相挤占
  • 推断CDNA（gfx950）的 MFMA 累加器在寄存器里，也没有按 warp 角色重新分配寄存器的机制；所有阶段塞进一个 kernel，就得按最大需求给每个 CTA 分配资源。拆开后每段可以各自用最合适的形状
  • 代价：GEMM1 和 GEMM2 之间多了一个同步点，本卡最慢的 GEMM1 tile 会拖住本卡所有 GEMM2；收益：实现简单，每段独立调优，不需要防死锁调度
  • 这是个真实的取舍，DeepGEMM 自己也在试拆分：PR #357 把 L1、L2 拆成两个 kernel，用 green context 分 SM 同时跑

③GEMM1 和 GEMM2 能不能融合

GEMM1 和 GEMM2 能不能 fuse？先看中间结果 h（SwiGLU 后的 [行数, 3072]）在三种做法里放在哪。

要点
  • DeepGEMM 的"融合"也要经过显存。它的好处是不用等 GEMM1 全部算完，并没有省掉这趟显存往返
  • 中间结果留在片上做不到：GEMM2 每个输出都要用 h 的整行 3072，而 h 是多个 CTA 按 N 方向分块算出来的
  • 让一个 CTA 包办一个 expert 的整个 FFN：每个 CTA 都得把这个 expert 约 35 MB 的权重读一遍，并行度只剩 M-tile 数。改成按 K 切分 GEMM2：部分和是 fp32 × 7168 = 28 KB/行，比 h 本身（3 KB/行）还大 9 倍

GEMM1 / GEMM2 融合：aiter 想融合有两条路
  1. 合成一个 persistent kernel：按 M-tile 计数（和 2.4 的 TILE_READY 同一套办法）；队列里先排 GEMM1、再排依赖它的 GEMM2，以此防死锁。

3.7L1 prepare：标志位时序

compact 的 prepare 里，三种 CTA 和另外 7 张卡之间靠一串标志位接力。从上往下就是时间顺序。

3.8L2 stage1：推数据与 GEMM1

一个 persistent kernel，前 32 个 CTA 先推数据，其余 CTA 等 tile 凑齐就算 GEMM1；推完的也加入计算。

一个 GEMM1 tile 里，数据怎么流：

# mega_moe_stage1.py:565-573：consumer 等某个 tile 凑齐
def _wait_tile_payload(flat):                    # flat = m_tile * N_TILES + n_tile
    tile_index = flat // N_TILES
    wait_i32_until_equals(tile_ready[tile_index], tile_expected[tile_index])
要点
  • 每推完一个 chunk，producer 先 fence，再给覆盖到的每个 tile 的 TILE_READY 原子 +1（dispatch.py:396-445）
  • 工作按 m_tile × N_TILES + n_tile 编号原子领取；expert 负载很偏时改成按完成顺序领（ready-order 队列），避免排在前面的 tile 迟迟不齐
  • A 走 LDS、B 直接进寄存器：一个 CTA 的 wave 只沿 N 切分，A（同一批行）被所有 wave 共用，所以放 LDS；B 每个 wave 各读各的列，没人共享，直接进寄存器省一次搬运

3.9L3 stage2：GEMM2 与回推

GEMM2 算完一块，epilogue 逐行看 srcmap，乘上权重，直接写进源卡的 comb_inp。

# mega_moe_stage2.py:102-170（摘要）
t = p & 0xFFFFFF;  s = p >> 24                       # p = srcmap
dest_pe = t >> log2(mtpr);  dest_lid = t & (mtpr - 1)
row_off = (dest_lid * topk + s) * token_nbytes + n_block * BN * elem_bytes
v = acc_row * weight                                 # 路由权重在这里乘，combine 不再乘
store(peer_base[dest_pe] + row_off, bf16(v) or fp8_1x32(v))
要点
  • stage2 内部没有任何等待，靠同一 stream 的 kernel 边界保证 stage1 已结束（2.11 的同步点就在这里）
  • 发出远端 store 后不等它完成，直接算下一个 m_block，所以回传和后续计算自然重叠
  • fp8 回传每行 7168 + 224 = 7392 B，约为 bf16（14336 B）的一半；mtpr ≥ 1024 时启用

3.10L4 combine：先集合，再求和

数据早就被别的卡写进来了，combine 只做两件事：确认所有卡都写完，再把 6 份结果加起来。

要点
  • 为什么要 barrier：别的卡的 GEMM2 写完、并且结果对本卡可见之后，才能求和。flag 由对方 combine 发出，而对方的 combine 在 stream 上排在它的 stage2 之后
  • 只有传 mask_invalid_slots=True 时才跳过 -1 slot；不传的话，那几行是上一次调用留下的旧数据，会被加进来
  • combine 固定用 current stream，而 prepare / stage1 / stage2 用调用方传的 stream。ATOM 不传 stream，没问题（3.16）

    • 做法：再预建一个容量 128 的实例（EP8 × 每卡 48 expert 时走 fixed-slot）。按当前 pass 全组统一、含 padding 的行数选实例；两个实例在所有卡上同序构建、在 graph capture 前建好；保留逐层换绑权重和 EPLB 视图
    • 开关：ATOM_MEGA_DECODE_FAST_PATH（默认开）；TBO、plugin、行数不统一或不支持的布局保持原容量
    • 验证：CPU 回归 133 passed / 3 skipped。8×MI355X、DeepSeek-V4-Pro、8k/1k、并发 512、不开 MTP：DPA + TBO → DPA + EP8 + EPLB + Mega，输出吞吐 +2.22%，TPOT −1.31%，P99 ITL +6.78%
    • 注意：上面是整套配置的对比，不是只开关这一项的消融；MTP 精度和多次运行方差未测（PR 里写明）
  2. 已合入ATOM #2463 + aiter #6127：DP pad 行屏蔽、decode 容量可调
    • 问题 1：DP-attention 下 pad 行照样走 dispatch / GEMM / combine，而且内容相同，全挤到同几个 expert 上，形成热点（2.10）
    • 做法 1：pad 行的 topk id 整行改成 -1；mask 在 device 上按 cu_seqlens_q[running_bs]（draft 用真实请求数 × q）算，graph 重放也生效；只在确实有 pad 行时请求 combine mask。开关 ATOM_MEGA_MASK_PAD_ROWS=1（默认关）
    • 问题 2：开 MTP 后 decode 图有 336 / 896 行，超过 128，退回大实例
    • 做法 2：ATOM_MEGA_DECODE_MTPR ∈ {128, 256, 512, 1024}；要继续走 fixed-slot，配套设 AITER_MEGA_FIXED_SLOT_MAX_MTPR = 511 / 1023 / 2047
    • aiter #6127：combine 跳过 -1 slot（supports_combine_mask）；fixed-slot 支持到 MTPR 1024；修复 ATOM 预热时会碰到的 Stage1 LDS 广播竞争
    • 验证：DeepSeek-V4-Pro DSpark DEP 3600 s agentic replay 零错误；同一容器 mask 开 / 关：GSM8K 5-shot 0.9545 / 0.9469（strict），DSpark 接受率 56.69% / 56.99%
    • 待补：吞吐数据。建议补两组对比：mask 开 / 关；ATOM_MEGA_DECODE_MTPR 128 / 512（开 MTP）

3.15优化机会：大小两个实例共用数据区

两个实例从不同时在跑。按代码推导，它们的数据区（3.12 里那几块大的）可以共用一份，控制面不行。

关键在于：别的卡往我的数据区写之前，总要先等到一次握手。

谁写入 rank d 的数据区写之前等了什么这说明 d 处于什么状态
compact producer 写 rx_em / scale_em / wts / srcmapd 的 PLAN_READY（dispatch.py:1638-1640，每个目标卡都有 producer 在等）d 已进入本次调用的 prepare，之前的 kernel 全部完成
fixed-slot producer 写同样几块owner 与所有卡的 LAUNCH_READY 握手d 已开始本次调用的 stage1
GEMM2 写 comb_inp本卡 stage1 已结束，而 stage1 的 producer 等过所有目标卡的 PLAN_READY 或握手目标卡已开始本次调用，上一次的 combine 已读完
_s1_out、comb_out只有本卡读写stream 顺序保证
要点
  • 控制面必须各一份：bigcnt 在握手之前就被写；信箱里放的是各实例自己的 epoch（mega_moe_v2.py:292-305）
  • 能省：默认配置每卡约 0.54 GB；为 MTP 把 decode 容量调到 512 时约 2.1 GB，大头在对称堆
  • 前提：每块按两者较大的需求分配；传 -1 时一定开 mask（两个实例在 comb_inp 里留下的旧数据格式不同）；两个实例不能同时在途
  • 改法：aiter 构造时允许传入外部数据区；ATOM 先建大实例，再把它的数据区交给小实例（flydsl_mega_experts.py:267-287）。验证：用 test_mega_moe_v2.py 交替调用，和不共用时逐位比对

3.16读代码时发现的问题

读源码时发现的 bug、隐患和可以改进的地方。

  1. bug已核实triton_mega_moe 分支会抛 TypeError
    • atom/model_ops/fused_moe/mori_v2_prepare_finalize.py:716 调用 self._recv_bound(topk_ids, arena_rows)；
    • 该类唯一的定义是 def _recv_bound(self, arena_rows)（:636），基类没有同名方法；
    • 进入路径 C（gfx1250 + ATOM_MORI_V2_FUSED=1 + ATOM_USE_TRITON_MOE=1）时会因多传一个位置参数报错；仓库里没有测试覆盖 mori_v2 或 triton_mega_moe。
  2. 按代码推导融合 shared expert 后 decode 快速路径失效
    • shared expert 一旦融合（LOCAL_REPLICA / EPLB_ROUTED），每 rank 49 个 slot，global_num_experts = 392；
    • aiter fixed-slot 条件 experts_per_rank == 48 不成立，所有 mtpr 都走 compact；
    • ATOM 的 experts == world * 48（flydsl_mega_experts.py:278）不成立，decode 小实例永远不会被选中；
    • flydsl_mega_experts.py:12-16 注释里的 "MTPR≤255 → fixed-slot" 只在每 rank 48 个 expert 时成立。

    官方 V4-Pro（shared FP8、routed FP4）不融合，不受影响。以后如需融合，可以放宽 gate 让 49 expert 也用小容量 compact 实例，或让 aiter fixed-slot 支持 epr = 49。

  3. 已核实aligned-pair 的 docstring 与实现不符

    mega_moe_stage2_aligned_pair.py:5-11 写 "scatters their weighted sum once"，但 _pair_routewise_half_scatter（:61-67）是 "Quantize/scatter A and B independently with one half-wave each"，分别写入两个 slot，相加发生在 combine。

  4. 已核实combine 不跟随传入的 stream

    prepare、stage1、stage2 用 forward(stream=...) 传入的 stream，combine 固定用 torch.cuda.current_stream()（flydsl_dispatch_combine_intranode_op.py:1308-1314）。ATOM 不传 stream，没有问题；以后要把 Mega 放到副 stream 上，必须先切换 current stream。

  5. 已核实分配公式comb_inp 过度分配

    见 3.12。fp8 wire 下约多分配 2.6 倍，M = 16384 时每个实例多占约 1.15 GB 对称堆。max_total_recv_tokens=W 已经把 legacy dispatch 区压到 8 行，comb_inp 却还按 legacy 的 W·M 计算。

  6. 已核实返回值与对称 buffer 别名

    见 3.10。所有层共用一个实例，任何需要让某层 MoE 输出跨过下一个 MoE 层存活的优化，都必须先拷贝出来。

  7. 优化待做GEMM1 / GEMM2 融合

    stage1 和 stage2 之间的 kernel 边界让先算完的 CU 空等本卡最后一个 GEMM1 tile。两条路：合成一个按 M-tile 计数的 persistent kernel，或两个 kernel 分 CU 并发、逐块放行。见 2.11。

  8. 按代码推导优化机会：大小两个实例的数据区可以共用

    见 3.15。现有握手已经保证"别的卡写我的数据区时，我之前的 kernel 都已结束"，所以数据区可以共用，控制面仍各自一份。默认配置每卡省约 0.54 GB；为 MTP 把 decode 容量调到 512 时约 2.1 GB，大头在对称堆。需要 aiter 支持从外部传入数据区。

  9. 未逐行复核子 agent 读出的小问题
    • mega_scheme（gm_scheme）参数只被存下，从未被读取；
    • idx_em、done2 等 legacy buffer 在 Mega 路径下分配了但不用；
    • 路径 B 中"量化 wire 必须用 mori dispatch"的注释已落后于 aiter：flydsl 的 TDM dispatch 已支持 scale 行。
