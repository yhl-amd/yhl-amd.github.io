LMCache 多进程模式 · ROCm · ATOM 上的 MiniMax-M3 MXFP4，TP4，agentic 负载

LMCache MP 每次 RPC 的时间花在了哪里

多进程（MP）模式下，LMCache server 用一个 Python 线程处理全部 4 个 TP rank 的 store 和 retrieve。在 ROCm 上，这个线程的时间主要耗在三件事上：每次销毁导入的 IPC event 都要等 GPU；每个请求都带着完整的 token 前缀；ObjectKey 一个一个按 dataclass 构造。三项都去掉后，与 MP 原版相比，store 执行时间降低 90%，KV 读回 p50 降低 75%，TTFT p90 降低 20%（三项全开的每一次都低于 inproc 的每一次）。

原版 server 每次 RPC 的三笔开销

MP 原版实测：store/retrieve 线程有 45% 的时间在忙，一次 store 平均执行 30.7 ms、排队 290 ms，一次 retrieve 开始前要排在 store 后面等 360 ms（p50）。约 46% 的时间有线程持有 GIL；在这些持有 GIL 的采样里（一次原版运行），ZMQ 线程上 msgpack 解码请求占 24%，导入 IPC event 占 10%，构造 ObjectKey 占 12%，blake3 哈希占 10%。

背景：一次 store / retrieve 里的两个 IPC event

ATOM 用 lmcache_driven 模式：启动时把每个 rank 的 KV cache 显存以 IPC handle 注册给 server，之后的拷贝由 server 在自己进程的拷贝 stream 上直接读写 ATOM 的显存。两个进程的 GPU 工作互相看不见，所以用两个跨进程（interprocess）event 在 GPU 上排先后，双方的 CPU 都不用等。

两个 event 的创建和销毁：原版 vs 改后（事件池）
一个 event 对象从新建/导入到销毁的存活期 ⊕ 新建或导入 │ record（在 stream 上插书签） wait 或 query ✕ 销毁 销毁时卡住 server 线程，等这张卡的拷贝做完
① 生产者 event（ATOM → server）② 完成 event（server → ATOM）
谁创建ATOM worker。每一步 forward 之前，start_load_kv() 新建一个 torch.cuda.Event(interprocess=True)，这一步所有的 load 和 save 共用（atom/kv_transfer/offload/mp/worker.py）LMCache server。每次 store / retrieve 新建一个（create_event()，lmcache_driven_transfer.py）
record 在哪ATOM 当前的 forward stream：它之前排的 GPU 工作，包括写这些 KV 的 forward，都在它前面server 自己的拷贝 stream，排在这次拷贝之后
拿来干什么server 的拷贝 stream 先 wait 它，所以拷贝一定排在 ATOM 之前提交的 GPU 工作之后：store 读到的是已经写好的 KV，retrieve 写这些 block 时之前排的工作也已做完ATOM 每一步在 get_finished() 里用 query() 查它（不阻塞）。到了之后，store 借来的 HBM block 可以释放，retrieve 的请求可以开始 forward
原版怎么传、怎么销毁每个请求带一个 handle；server 每次导入，store() / retrieve() 返回时销毁，销毁阻塞到这张卡的拷贝做完server 导出后放进 2048 的环形队列保活（注释：防止引擎访问已失效的 event），满了挤掉最老的并销毁；ATOM 每次导入一个，future 释放时销毁
改后（事件复用）adapter 在同一 stream 位置 record 一个池里的 event（16 个轮转，每个 record 31 次后换新，绕开 ROCm 7.2.4 的 32 次限制）；server 每个 handle 只导入一次并缓存。ATOM 自己每步仍新建一个 event、操作完成后仍销毁（ATOM 代码没改），只是不再发给 serverserver 每个 GPU 上下文一个 512 个的池，重复 record；ATOM 每个 handle 只导入一次

销毁会阻塞是在 ROCm 7.2.4 上实测的行为（mm3/test_event_reuse.py）：销毁导入的或自己建的 interprocess event，都要等本进程在这张卡上排着的 GPU 工作做完，GPU 空闲时 0.27 ms，忙 50 ms 时 49.9 ms；其他进程的工作不影响。为什么会这样（HIP 内部实现）没有查到源码层面的原因。原版里 producer event 是 store() 的局部变量，函数一返回就被释放，所以回复要等这次销毁结束才发出。

handler 的 CPU 处理（约 3 ms） 销毁导入的 event：线程卡住，等这张卡的拷贝做完 GPU 拷贝 原版 只开事件复用 三项全开

上半部分是示意：rank 2 和 rank 3 各发来一个 16k token 的 store，handler 约 3 ms 是实测量级，每次拷贝按 16k × 23.4 KB ≈ 383 MB 估成 20 ms。原版里线程处理完 rank 2 就卡在销毁 event 上，直到 GPU 2 拷完才去处理 rank 3，两张卡的拷贝被串成一条，后面的 retrieve 跟着排队；改后线程排完拷贝就返回，两张卡同时拷。完成 event 的环形队列满了之后挤掉的那个也会阻塞（单卡实测），多卡时具体等哪张卡没有单独测，图中没画；client 端每次导入、用完销毁完成 event 的耗时在 ATOM 里也没有单独测。下半部分是实测：微基准见 mm3/test_event_reuse.py；中间 4 组是端到端压测里 server 的统计（原版 3 次、只开事件复用 2 次、三项全开 3 次运行的均值），每组以原版为满长；最后 2 组是只压 server 的测试里一批会话同时到达、全部做完一轮的时间。单开事件复用后 store 从 30.7 降到 19.0 ms，剩下的部分要靠另外两项（client 哈希、批量构造 key）一起去掉，三项全开才到 3.0 ms。

图解 ②-1：一个 store 请求里装的是什么，原版传全部 token，改后只传块哈希

例子取自下图那一轮：rank 2 存这一轮新算的块 536–599（token 137,216–153,599）。块哈希是链式的：hk = blake3(hk−1 ‖ 第 k 块的 256 个 token)，h0 前面接的是 none_hash，所以任何一块的 key 都取决于它前面的全部 token。原版协议只让 server 算哈希，client 只能每次从第 0 个 token 发起；server 的 session 缓存了前面的哈希时只补算新块，但 token 照样整段发、整段解码、整段拷进 session。改后 client 的 adapter 按请求缓存已算过的哈希，每步只补算新块，计算规则与 server 的 TokenHasher 逐字节相同（已测）；ATOM 的 load/save 两端都按 256 对齐、总是接在已有前缀后面，所以一段范围完全可以用这几块的哈希描述。

图解 ②-2：一轮对话里每个 RPC 带了什么，原版 vs 改后（client 哈希）
原版：带着、但这个 RPC 用不上的前缀（token） 原版：这个 RPC 真正要处理的范围（token） 改后：只带这段范围的块哈希（每块 32 B）

示例：多轮对话中的一轮，prompt 共 153,600 token（600 块，每块 256 token）。前 100,352 个 token 还在 GPU 前缀缓存里，LMCache 命中到 137,216，最后 16,384 个是新 token，一步 prefill 完。每个 RPC 带哪段 token 取自 ATOM 代码：lookup 和 free_lookup_locks 带整段 prompt（_lookup_token_ids()），retrieve 带 token_ids[:transfer_end]，store 带 token_ids[:aligned]，end_session 只带 request_id；retrieve 和 store 由 4 个 rank 各发一次。字节数是用本次压测的真实 prompt 实测的：aiperf 生成的数据集经 M3 的 chat template 分词后，msgpack 平均每个 token 占 2.78 B（8% 的 id ≥ 65,536，要 5 B）；153,600 个 token 解码实测 2.2–2.5 ms，图中按 2.35 ms 折算。改后每个块哈希 32 B，带哈希的 key 实测解码 0.7–0.8 µs（mm3/micro_hashkey.py）。原版 server 算哈希的块数按代码推算：lookup 用 compute_chunk_hashes 从头算整段，free_lookup_locks 也要从第 0 块算到 end，retrieve 和 store 走 session 增量计算、4 个 rank 共用同一个 session。鼠标悬停每一行可看说明。

1. 销毁导入的 IPC event 要等 GPU

每次 store 和 retrieve 都会导入 client 的 event，处理函数返回时把它销毁；同时还会新建一个完成 event，容量 2048 的环形队列满了之后就销毁最老的一个。在 ROCm 7.2.4 上，这个销毁会一直阻塞到本进程在这张卡上排队的 GPU 工作做完（在单卡上实测；其他进程的工作不影响）。于是这一个线程每次都要等自己刚提交的拷贝做完，才能处理下一个请求（前后对比见上面的图解 ①）。

实测（2 个进程，1 张 GPU）GPU 空闲本进程 GPU 忙 50 ms
导入 event（from_ipc_handle）0.012 ms0.040 ms
销毁导入的 event0.27 ms49.9 ms

举例：rank 2 发来一个 16k token 的 store

  1. ATOM 的 rank 2 做完一步 prefill，下一步开始前在 forward stream 上 record 一个 interprocess event，把 event 的 handle 和这 16k token 对应的 128 个 block 号一起发给 server。
  2. server 的 store/retrieve 线程进入 store()（lmcache_driven_transfer.py）：先 create_event() 新建一个完成 event，再 import_event() 即 Event.from_ipc_handle 打开 ATOM 的 event（0.04 ms）。
  3. wait_event() 让 server 的拷贝 stream 等 ATOM 那一步 forward 写完 KV，然后把 128 个 block × 2.99 MB = 383 MB 拷到 CPU 的拷贝排进 GPU 2 的 stream，record 完成 event。这几步只是排队，CPU 上约 3 ms。
  4. export_event() 把完成 event 放进容量 2048 的环形队列；队列已满，最老的那个完成 event 被销毁，这个销毁同样会阻塞到 GPU 上排着的拷贝做完（单卡实测会阻塞；多卡时具体等哪张卡没有单独测）。
  5. store() 返回时，局部变量 producer_event（在 GPU 2 上导入的 ATOM event）被销毁：阻塞到 GPU 2 上刚排进去的 383 MB 拷贝做完，约 20 ms。
  6. 这时线程才去取下一个请求，比如 rank 3 的 store。于是 GPU 3 的拷贝要等 GPU 2 的拷贝做完才开始，4 张卡一张接一张；排在后面的 retrieve 要等这 4 个 store 依次做完才轮到（上面图里等了 82 ms）。

改后：ATOM 的 producer event 来自一个轮转池，server 每个 handle 只导入一次、一直保留；完成 event 也来自池子，重复 record，不再销毁。store() 排好拷贝就返回（约 3 ms），4 张卡并行拷贝。

2. 每个 RPC 都带着整段 token 前缀

ATOM 在每一次 lookup、store、retrieve 和 free_lookup_locks 里都发送从第 0 个 token 开始的整段前缀，每个 rank 都发，每一步 prefill 都发，前缀越长请求越大（一个请求里装的是什么、一轮里各 RPC 带了什么，见上面的图解 ②-1 和 ②-2）。server 在 ZMQ 线程上持有 GIL 解码它，再拷进 session，并对新增的块做哈希。下图是另一个例子：长 prompt 第一次 prefill 时，store 的请求体逐步变大。

举例：一个 153,600 token 的 prompt，prefill 每步 16k，共 10 步

  1. scheduler 发 lookup：key 里是整段 153,600 个 token（0.43 MB）。server 的 ZMQ 线程解码成 Python 元组，2.2–2.5 ms，期间持有 GIL，其他线程都得等。
  2. 第 1 步 prefill 完，4 个 rank 各发一个 store，key 里带 [0, 16,384)；第 2 步带 [0, 32,768)……第 10 步带 [0, 153,600)。ATOM 这样构造 key：token_ids=list(seq.token_ids[:aligned])，每一步都从 0 开始。
  3. 每个 store 到了 server：ZMQ 线程解码整段前缀；store/retrieve 线程里 resolve_obj_keys() 再执行 session.set_tokens(list(key.token_ids))，把整段拷一份进 session，替换并释放上一份；然后对新增的 64 块做哈希。
  4. 合计：40 个 store 共带 356 万个 token（约 10 MB），ZMQ 线程光解码就要约 55 ms。之后这个请求的 retrieve、free_lookup_locks 也都各带一次整段前缀。

改后：adapter 按请求增量算好块哈希，store 只带本步 64 块的哈希（2 KB），lookup 带 600 块（19 KB）；server 不再解码、拷贝和哈希 token。

3. ObjectKey 逐个按 frozen dataclass 构造

TP4 下对一个 153,600 token（600 块）的 prompt 做 lookup，要构造 2,400 个 ObjectKey（600 个块 × 4 个 rank），每个都走 frozen dataclass 的 __init__，再用 __post_init__ 重复校验同样的 model name 和 salt。free_lookup_locks 和 end_session 还要再来一遍。

2,400 个 key耗时
dataclass 构造1.67 ms
只校验一次、批量构造0.44 ms

举例：上面那个 prompt 的 lookup、free_lookup_locks 和 end_session

  1. lookup 线程先用 compute_chunk_hashes 把整段 prompt 从头哈希一遍，得到 600 个块哈希，约 2.6 ms。上一轮请求已经哈希过几乎同样的前缀，但每个请求的 session 是独立的，用不上。
  2. ipc_key_to_grouped_object_keys() 为 4 个 kv rank 各建一行，每行 600 个 ObjectKey(chunk_hash, model_name, kv_rank, object_group_id, cache_salt)，共 2,400 个。
  3. 每构造一个，frozen dataclass 都要用 object.__setattr__ 设 5 个字段，再跑一遍 __post_init__：model_name 里有没有 @、object_group_id 是否小于 0、cache_salt 里有没有禁用字符、salt 长度是否超过 128。2,400 次检查的都是同一个 model_name 和同一个 salt。
  4. 之后 free_lookup_locks 为没读回的部分再建一遍 key；end_session 为整个会话的所有块（prompt 加上生成的部分）× 4 个 rank 再建一遍，用来在 LRU 里 touch；每个 store/retrieve 也为自己那 64 块建 key。

改后：同一次调用只校验一次 model_name、group 和 salt，然后批量填字段，2,400 个从 1.67 ms 降到 0.44 ms。端到端里 lookup 处理时间主要是靠 client 哈希降下来的（51 → 24 ms），单开这一项只降约 7%。

原型改动

三项改动都需要显式开启，并保持新老 client 和 server 之间的协议兼容：新字段都有默认值，client 不设置就和原来一样。

  • 事件复用（client 端 LMCACHE_MP_POOLED_EVENTS=1）。adapter 在引擎 event 所在的 stream 位置上 record 一个池里的 producer event；server 每个 handle 只导入一次并一直保留。server 返回的完成 event 来自每个实例 512 个的池，会被重新 record；这些 handle 带一个标记，client 每个只导入一次。不再有任何导入的 event 按操作销毁。client 只用 query() 轮询完成 event，看到的完成只会更晚、不会更早，因为同一个实例的操作在同一条 stream 上按顺序执行。
  • client 端算块哈希（client 端 LMCACHE_MP_CLIENT_HASH=1）。adapter 用 server 自己的 blake3 规则按请求增量计算哈希（与 TokenHasher 逐字节相同），只在新增的 IPCCacheServerKey.chunk_hashes 字段里发送 [start, end) 的 32 字节哈希，token_ids 留空。新请求哈希整段 prompt：单独测 150k token 要 2.2 ms，压测时 worker 调用线程上 128k 要 4.7 ms（见「挪到 client 端的开销」）；之后每增加 16k token 约 0.2 ms。
  • 批量构造 ObjectKey（server 端 LMCACHE_MP_FAST_KEYS=1）。同一次调用共享的字段只校验一次，构造时不再逐个走 dataclass 构造函数。

ROCm 7.2.4 限制了 event 复用：IPCEvent::streamWait 用 signal[read_index] 取槽位，没有像 record 和 query 那样对 32 取模（clr develop 分支已修）。对端要 stream-wait 的 event，在被 record 32 次以内才能正常等待，所以 producer event 每 record 31 次就换一个。完成 event 只被 query，可以一直复用。两种用法都在双进程下跑了 200 轮，没有出现提前完成或读到旧状态。

条形是一组的均值，圆点是各次运行。三项全开与 MP 原版相比：TTFT p90 低 20%，每一次都低于原版的每一次（3 次 vs 3 次）；TTFT 均值低 7%，范围重叠（3 次 vs 3 次）；TTFT p99 低 11%，范围重叠（3 次 vs 3 次）；排队时间均值高 3%，范围重叠（3 次 vs 3 次）。读回超过 1 s 的次数：每次运行 67 → 19，每一次都低于原版的每一次（3 次 vs 3 次）。server 端单次 RPC 的指标变化倍数大、重复性好；p90 以外的客户端时延在同一组的不同运行之间也有波动（inproc 也一样），我们没有分离出原因。

server 单独压测

同一个 server，不跑模型，直接用 ATOM 自己的 LMCache adapter 类驱动：4 个 worker 进程分别在 4 张 GPU 上注册 MiniMax-M3 形状的 page view（301 个张量，每 rank 每 token 23,400 字节），第 5 个进程扮演 ATOM 的 scheduler。对话的每一轮依次是：lookup → 每个 rank 读回前缀 → 每个 rank 存入新增的 16k token（key 里带完整 prompt）→ end_session。写入总量远低于 L1 容量，不会发生淘汰。

sweep：单个会话，prompt 从 16k 以 16k 为步长增长到 524,288 token，顺序执行；共跑两遍（每遍 token 都是新的），只统计第二遍，每个点是一次测量。为了图清楚，只开「批量构造 key」这一组没画进图，五组的数据都在表里。鼠标悬停可看具体数值。

挪到 client 端的开销

worker 的提交调用在调用线程上花的时间（在 ATOM 里就是 model runner 的线程），按 prompt 长度列出 sweep 第二遍的中位数。原版把 token 前缀的编码放在 client 的后台消息线程上，所以调用本身返回很快。开启 client 哈希后，新请求的第一次操作要在调用线程上把整段 prompt 哈希一遍，同一请求之后的操作只哈希新增的块。sweep 每一轮都是新请求，所以 retrieve 那几列就是整段哈希的开销。

正确性

  • 单元测试：client 算的哈希与 TokenHasher.compute_chunk_hashes 一致（整段和增量都测）；老格式的 key 解码后新字段取默认值；批量构造的 ObjectKey 与 dataclass 构造的相等，哈希值也相同。
  • 真实 server、单卡：200 个请求存入随机 KV 再读回到另一组 block，store、lookup、retrieve 之间交叉使用 token 模式和哈希模式的 key，完成 event 池设为 8 以强制反复复用：所有 lookup 都完整命中，读回的每个 block 逐字节一致。
  • ATOM 重启测试：8 个 27k–94k token 的大海捞针 prompt；重启 ATOM 后，每个 prompt 的 KV（每 rank 共 485k token）都从 LMCache 读回。原版和补丁在重启前后都是 8/8 答对，两者 16 次生成的文本逐字相同。

这组数据的局限

  • 只有一个节点、一个模型、一种负载，只测了 ROCm 7.2.4。CUDA 上销毁 IPC event 的开销没有测。
  • 只开单项改动的几组分别只有 2、2、1 次运行；同一组不同次之间端到端 TTFT 会差 10–30%，所以单项的端到端数字只作参考。server 的执行时间在多次之间相差不到几个百分点；排队时间波动更大，但各组之间差得很开。
  • 三项全开后 save 完成得更快，因为 save 未完成而被扣住的 HBM block 少了很多（原版每次 2,710–8,820 个，补丁 432–548 个）。在总命中率相同的情况下，从 LMCache 读回的 token 平均低 9%，范围重叠（3 次 vs 3 次），所以端到端的变化里可能有一部分来自更多前缀留在了 HBM。这一点没有单独分离。
  • MP 的运行带有跟踪开销（EventBus 订阅、逐 RPC 计时、60 s 的 py-spy），inproc 的运行没有。
  • inproc 第 3 次试了三次才成功：前两次都是紧跟在一个释放了 1 TB 以上锁页内存的进程之后启动，某个 rank 分配 257 GB 锁页 CPU 缓存时卡住，其他 rank 的 NCCL 初始化等 300 s 超时。成功的那次启动花了 18 分钟；测量窗口从 server 就绪之后开始计算。
  • client 端算哈希会把 client 和 server 的哈希规则绑在一起（blake3，256 token 一块）；原型在 server 端检查算法，不一致就拒绝。

给 LMCache 的建议

  • 不要按操作销毁导入的 IPC event。按 handle 缓存导入结果并复用完成 event，或者把销毁移出请求路径。在 server 单独压测的 sweep 里，只做这一项就让 retrieve 执行时间降低 65%（197 → 69 ms），是对 store/retrieve 处理函数影响最大的单项改动。
  • 不要每次都重发 token 前缀。可以约定块哈希的规则，让 client 直接发哈希；也可以让 session 接受 token 增量。现在请求体随 prompt 增长，每个 rank 的每次 RPC 都要发一遍。如果把哈希挪到 client，应该每个请求只算一次（scheduler 做 lookup 时已经哈希过整段 prompt）再下发给各 worker，或者放到 model runner 线程之外去算；这个原型是在每个 worker 的调用线程上算的。
  • 批量构造 ObjectKey，改在 ipc_key_to_object_keys 和 ipc_key_to_grouped_object_keys 里。
  • lookup 是下一个瓶颈。做完这些改动后，大部分 GIL 时间落在 lookup 线程上：构造 key、L1 读锁、touch。
  • 提醒在 ROCm 7.2 上复用 IPC event 的人：对端会 stream-wait 的 event，要在第 33 次 record 之前换掉。
