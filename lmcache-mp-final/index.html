1. 总览图解：原版 vs 四项全开

例子：一个 153,600 token 的 prompt 在 prefill 最后一步，4 个 rank 同时发来 store；同时另一个新请求发来 lookup。CPU 部分按实测量级画：解码一个带整段 token 的请求 2.4 ms，哈希整段 prompt 2.6 ms，构造 2,400 个 ObjectKey 1.7 ms（批量 0.44 ms），handler 约 3 ms；拷贝 383 MB 按 20 ms 估。

解码整段 token（持有 GIL） 哈希整段 prompt / 逐个构造 key handler 处理（约 3 ms） 卡在销毁 event，等拷贝做完 排队，GPU 空等 GPU 拷贝
  • 原版：ZMQ 线程先把 5 个请求里的整段 token 逐个解码（共约 12 ms，期间持有 GIL）；唯一的 store/retrieve 线程处理完一个 rank 就卡在销毁上等这张卡拷完，4 张卡的拷贝串成一条，约 94 ms 才全部完成；lookup 线程还要把整段 prompt 重新哈希、逐个构造 2,400 个 key。
  • 四项全开：请求里只有块哈希，解码几乎不花时间（第 2 项）；lookup 线程不用再哈希，key 批量构造（第 2、3 项）；4 个线程各管一个 rank（第 4 项），处理完不再卡在销毁上（第 1 项），约 23 ms 全部完成。

2. 背景：一次 store / retrieve 里发生了什么

ATOM 把 KV cache 显存注册给 LMCache server，server 在自己的拷贝 stream 上直接读写 ATOM 的显存。每次 store / retrieve：

  1. ATOM 发一个 RPC，带 key（原版是从第 0 个 token 开始的整段 token 前缀）、block 号和一个跨进程 event 的 handle；
  2. server 解码请求，用 token 算出每块的哈希，构造 ObjectKey，在 L1 里分配或查找；
  3. server 用两个跨进程 event 和 ATOM 在 GPU 上排先后（下表），排好拷贝后回复。
① 生产者 event（ATOM → server）② 完成 event（server → ATOM）
意思“KV 写完了，可以拷”“拷完了，block 可以放 / 请求可以跑”
谁插ATOM，插在写 KV 的 forward 后面server，插在拷贝后面
对方怎么用server 的拷贝 stream 先 wait 它（在 GPU 上等）ATOM 每步 query 它（不阻塞）
原版生命周期server 每次导入，用完销毁server 每次新建；ATOM 每次导入，用完销毁

3. 优化 1：IPC event 复用（事件池）

3.1 问题：销毁 event 会卡住线程

  • ROCm 7.2.x 上销毁跨进程 event 走 ~IPCEvent → ihipHostUnregister → SyncAllStreams，要等本进程在这张卡上排着的所有工作做完才返回（rocm-systems#7520；develop 已由 #7710 修复，7.2 的 backport #11529 未合）。
  • 销毁期间，别的线程新建跨进程 event 也会被卡住（实测 43 µs → 38.6 ms）。
  • 原版每次 store/retrieve 都要新建、导入、销毁 event，每次操作卡一次。LMCache dev 的 #5439 把销毁挪到了另一个线程，但每次操作还是要销毁。

卡住的时间是在等拷贝，不是销毁本身：

销毁本身（约 1.3 ms） 销毁在等 GPU 排空（SyncAllStreams） 这张卡上的 GPU 工作
实测：销毁耗时随“卡上排着的工作”线性增加

MI355X，ROCm 7.2.4。虚线是“销毁耗时 = 排着的工作 + 1.3 ms”。

真实服务里卡得更久

3.2 改法：event 反复 record，handle 只导入一次

CPU 正常处理 GPU 工作 销毁 event：线程卡住，等这张卡拷完 在等 / 排队 ② 到了，block 可以放
原版（每次操作）事件池
① 生产者 eventATOM 每步新建client 16 个轮换 record；每个记满 31 次换新（绕开 ROCm 7.2.x 的 32 次 bug）
server 导入 ①导入 1 次 + 销毁 1 次每个 handle 只导入 1 次，缓存，不销毁
② 完成 event每次新建；队列满后每次再销毁 1 个每个实例 512 个轮流 record，不销毁
ATOM 导入 ②导入 1 次 + 销毁 1 次只导入 1 次，缓存
合计新建 1、导入 2、销毁 3稳定后 0
  • 为什么安全：record 是把 event 挪到新位置，wait/query 看的总是最近一次；被提前重新 record 时，对方只会看到同一条 stream 上更靠后的位置，只会多等，不会提前放行。两进程互相复用 400 轮：0 次提前放行、0 次误报。
  • 不会泄漏：写入相同数据量时，原版和事件池占用的 L1 内存一样（8 万个 chunk 后 485 GB 对 484 GB）。

4. 优化 2：token hash 挪到 client，不再发整段 token

KV 块的 key 是链式哈希：hk = blake3(hk−1 ‖ 第 k 块的 256 个 token)，任何一块的 key 都取决于它前面的全部 token。原版协议只让 server 算哈希，所以 ATOM 在 lookup、store、retrieve、free_lookup_locks 里每次都发从第 0 个 token 开始的整段前缀，每个 rank 都发，前缀越长请求越大；server 在 ZMQ 线程上持有 GIL 解码，拷进 session，再哈希。改后由 client 按请求增量算好块哈希，RPC 里只带这段范围的哈希。

图解 ②-1：一个 store 请求里装的是什么，原版传全部 token，改后只传块哈希

例子取自下图那一轮：rank 2 存这一轮新算的块 536–599（token 137,216–153,599）。块哈希是链式的：hk = blake3(hk−1 ‖ 第 k 块的 256 个 token)，h0 前面接的是 none_hash，所以任何一块的 key 都取决于它前面的全部 token。原版协议只让 server 算哈希，client 只能每次从第 0 个 token 发起；server 的 session 缓存了前面的哈希时只补算新块，但 token 照样整段发、整段解码、整段拷进 session。改后 client 的 adapter 按请求缓存已算过的哈希，每步只补算新块，计算规则与 server 的 TokenHasher 逐字节相同（已测）；ATOM 的 load/save 两端都按 256 对齐、总是接在已有前缀后面，所以一段范围完全可以用这几块的哈希描述。

图解 ②-2：一轮对话里每个 RPC 带了什么，原版 vs 改后（client 哈希）

原版：带着、但这个 RPC 用不上的前缀（token） 原版：这个 RPC 真正要处理的范围（token） 改后：只带这段范围的块哈希（每块 32 B）

示例：多轮对话中的一轮，prompt 共 153,600 token（600 块，每块 256 token）。前 100,352 个 token 还在 GPU 前缀缓存里，LMCache 命中到 137,216，最后 16,384 个是新 token，一步 prefill 完。每个 RPC 带哪段 token 取自 ATOM 代码：lookup 和 free_lookup_locks 带整段 prompt（_lookup_token_ids()），retrieve 带 token_ids[:transfer_end]，store 带 token_ids[:aligned]，end_session 只带 request_id；retrieve 和 store 由 4 个 rank 各发一次。字节数是用本次压测的真实 prompt 实测的：aiperf 生成的数据集经 M3 的 chat template 分词后，msgpack 平均每个 token 占 2.78 B（8% 的 id ≥ 65,536，要 5 B）；153,600 个 token 解码实测 2.2–2.5 ms，图中按 2.35 ms 折算。改后每个块哈希 32 B，带哈希的 key 实测解码 0.7–0.8 µs（mm3/micro_hashkey.py）。原版 server 算哈希的块数按代码推算：lookup 用 compute_chunk_hashes 从头算整段，free_lookup_locks 也要从第 0 块算到 end，retrieve 和 store 走 session 增量计算、4 个 rank 共用同一个 session。鼠标悬停每一行可看说明。

改法要点和代价

  • ATOM 侧 adapter 用和 server TokenHasher 完全相同的规则（blake3，256 token 一块）按请求增量算哈希，逐字节一致（已测）；ATOM 的 load/save 两端都按 256 对齐，一段范围完全可以用这几块的哈希描述。
  • server 不再解码、拷贝和哈希 token。真实服务里 lookup 执行 51.4 → 23.7 ms，ZMQ 接收线程持有 GIL 的采样 683 → 18。
  • 代价挪到了 client：新请求第一次操作要在调用线程上把整段 prompt 哈希一遍（128k 约 4.7 ms），之后每增加 16k 约 0.2 ms。更好的做法是 scheduler 做 lookup 时算一次再下发给各 worker。
  • client 和 server 的哈希规则绑在了一起；server 端会检查算法，不一致就拒绝。

5. 优化 3：批量构造 ObjectKey

TP4 下对一个 153,600 token（600 块）的 prompt 做 lookup，要构造 2,400 个 ObjectKey（600 块 × 4 个 rank）。每个都走 frozen dataclass 的 __init__，再用 __post_init__ 校验 model name 有没有 @、group 是否小于 0、salt 有没有禁用字符和是否超长——2,400 次校验的都是同一个 model name 和同一个 salt。free_lookup_locks 和 end_session 还要再来一遍。

构造 2,400 个 ObjectKey 的耗时（ms）
改法
  • 同一次调用共享的字段（model name、group、salt）只校验一次，然后批量填字段，不再逐个走 dataclass 构造函数。
  • 批量构造出来的 key 与 dataclass 构造的相等，哈希值也相同（单元测试）。
  • 单项收益不大（lookup 执行约 −7%），但它和第 2 项一起，把 lookup / free_lookup_locks / end_session 的 CPU 时间压下来。

6. 优化 4：--max-gpu-workers 4

6.1 问题：4 个 rank 排成一队

LMCache server 用 --max-gpu-workers 个线程处理 store/retrieve，默认 1。每个 rank 第一次来时分到一个线程，以后它的请求都交给这个线程按顺序处理。ATOM TP4 有 4 个 rank，线程只有 1 个，全挤在一起。server 日志里有现成的警告：

LMCache WARNING: AffinityThreadPool: affinity_key=... wrapped onto worker slot 0 (only 1 workers),
    so it shares a thread with an earlier key and their tasks are serialized.

真实服务的 server trace 里，retrieve 在 server 上排队中位数 0.65–0.86 s，真正执行只要 18 ms。

6.2 改法，以及为什么要和事件池一起用

  • 线程数设成 rank 数（TP4 就是 4），每个 rank 一个线程，4 张卡的请求并行处理。同一个 rank 的请求仍是一个接一个，再多开用不上；多个 ATOM 实例共用一个 server 时按 client 总数来设。
  • 只开 4 个线程，每个线程还是“办一件、等一会儿”（卡在销毁上）；加上事件池，办完马上接下一个。下图：4 个线程都开着，看同一个 rank 连续来 3 个请求：
线程处理请求（约 3 ms） 线程卡在销毁 event，等这张卡拷完 GPU 拷贝（约 20 ms） ATOM 收到“拷完了”的通知

7. 配套修复：和 mono 一起用时避免 GPU 卡死

一句话：ROCm 7.2 上，server 在 GPU 上等 ATOM 的 IPC event（①），实际是启动一个只有 1 个线程的轮询 kernel。ATOM 的 mono kernel 要求 256 个 CTA 同时驻留（每个 CU 一个）并互相自旋等待。轮询 kernel 一旦先占住某个 CU 的槽位，mono 的那个 CTA 就进不去；而轮询 kernel 等的信号要等 mono 跑完才会写——两边互相等，GPU 卡死。修复：不在 GPU 上等一个还没完成的 event。

7.1 为什么会卡死

  • 7.2 的 IPC event 是一块共享内存里的信号槽。server 调 stream.wait_event → ROCCLR_COMMAND_STREAM_WAIT_VALUE；rocclr 默认（GPU_STREAMOPS_CP_WAIT=false）用一个 1 个 work-item 的 blit kernel streamOpsWait 反复读这块内存，直到值变成 0。
  • ATOM mono（ATOM_MONO_ENABLE 默认开；DSV4、GLM-5.2、MiniMax-M3 都有）：mono/config.py 写明 “one CTA per CU, all co-resident”，CTA 之间自旋等待，靠的就是全部同时在 GPU 上。
  • server 和 ATOM 跑在同一张卡上。ATOM 发请求时往往还没等 ① 完成；如果 server 的轮询 kernel 先上了 GPU、占了某个 CU 的槽位，随后派发的 mono 就有一个 CTA 进不去。
mono 的 CTA（每个 CU 一个，互相自旋等待） server 的轮询 kernel（等 ①） 进不去 / 在等 server 拷贝 server CPU 处理

7.2 修复：两层，都默认关

开关位置做什么
LMCACHE_MP_SUBMIT_AFTER_PRODUCER=1client（ATOM adapter）store/retrieve 交给后台线程，在 CPU 上轮询 ① 完成（query() 只读主机内存）后再发送；submit 立即返回一个 future，发送前报告未完成。ATOM 的调用线程不阻塞。
LMCACHE_MP_HOST_WAIT_PRODUCER=1server先在 CPU 上查 ①：已完成就不排 GPU 等待；未完成（老 client 提前发了）就在 CPU 上轮询，不再往 GPU 上排轮询 kernel。
  • 剩下的 server kernel（拷贝、记录 ② 的写信号 kernel）都不依赖 mono，能自己跑完，最多让 mono 晚开始一点，不会循环等待；ATOM 对 ② 只在 CPU 上 query()。
  • 正确性：7.2 写信号前有一个 release barrier，CPU 看到 ① 完成时，ATOM 写的 KV 已经可见，再排拷贝顺序成立。
  • 根治要等 ROCm：develop 已合入 #5575，改用由 CP 等待的 ROCr IPC 信号，不再有轮询 kernel；还没进 7.2。

9. 怎么用

# ATOM（LMCache client）侧
export LMCACHE_MP_POOLED_EVENTS=1   # 优化 1：事件池
export LMCACHE_MP_CLIENT_HASH=1     # 优化 2：client 算块哈希（需 blake3 server）

# LMCache server 侧
export LMCACHE_MP_FAST_KEYS=1       # 优化 3：批量构造 ObjectKey
lmcache server ... --max-gpu-workers 4   # 优化 4：每个 rank 一个线程（TP4 → 4）

# 配套修复：和 mono 一起用时必须开（避免 GPU 卡死）
export LMCACHE_MP_SUBMIT_AFTER_PRODUCER=1   # client：① 完成后再发送
export LMCACHE_MP_HOST_WAIT_PRODUCER=1      # server：不在 GPU 上等未完成的 ①
  • 前三项默认都关，需要显式开启；新字段都有默认值，新老 client / server 互相兼容。
  • 代码：三项都在 #2（f22dec28）；事件池已移植到 dev：#3。
  • L1 要留余量：处理变快后同时在途的写入更多，L1 默认边用边扩（lazy），扩容跟不上会提前触发淘汰；可用 --l1-init-size-gb 让启动时先扩出足够容量。

10. 注意事项

  • 和 mono 一起用必须开配套修复（第 7 节）：否则 ROCm 7.2 上 server 的轮询 kernel 可能和 mono 互相等，GPU 卡死。
  • L1 扩容会挡住 HIP 调用：L1 默认边用边扩，每次用 hipHostRegister 锁 10 GB，锁的几秒里 server 的 IPC event record、注册时打开显存句柄都会被挡住，表现为约 10 s 的卡顿、注册超时、实例被 server 回收（Reaped GPU instance）。线上要么用 --l1-init-size-gb 一开始就扩够，要么接受偶发卡顿。
  • 心跳 / 注册卡住：ATOM 文档目前要求不要多开 GPU worker（多线程懒初始化曾把 server 卡到超过心跳）。压测里注册卡住在 1 个和 4 个线程时都出现过，触发条件没查清；上线前看 server 日志有没有 Reaped GPU instance、注册超时。
  • 事件池只针对 ROCm：CUDA 上销毁 event 不同步，收益小很多；ROCm 7.2 的 backport（#11529）合入后，销毁阻塞本身会消失。
  • token hash 把哈希开销挪到了 client 调用线程（新请求 128k 约 4.7 ms）；最好由 scheduler 算一次再下发。
  • 真实服务的 TTFT 均值、p99 波动大，单项端到端数字只作参考；server 侧指标的倍数大、重复性好。

11.1 sweep 详细复现步骤

  1. 环境：一台 4 卡 MI300/MI350 级机器；镜像 rocm/atom-dev（我们用 10-28 构建的 latest，ROCm 7.2.4、torch 2.10，自带 LMCache f22dec28）。 
    docker run -d --init --name lmc_sweep --network host --ipc host --device /dev/kfd --device /dev/dri \
  --group-add video --security-opt seccomp=unconfined -e HIP_VISIBLE_DEVICES=4,5,6,7 \
  -v /path/to/work:/w rocm/atom-dev:latest sleep infinity
docker exec -it lmc_sweep bash
  2. 准备两份 LMCache：原版直接用镜像自带的；补丁版 = 拷一份镜像自带的，再覆盖 PR #2 改过的 9 个 Python 文件（C++ 扩展不变）。 
    git clone https://github.com/yhl-amd/LMCache.git /w/LMCache && cd /w/LMCache
git checkout perf/mp-pooled-events
mkdir -p /w/site-pool-f22 && cp -a /opt/venv/lib/python3.12/site-packages/lmcache /w/site-pool-f22/
git diff --name-only f22dec2832124ea4ffeb464553b819a6369d4a30 HEAD -- lmcache | xargs -I{} cp --parents {} /w/site-pool-f22/
PYTHONPATH=/w/site-pool-f22 python -c "import lmcache.integration.atom.multi_process_adapter as m; print(m._POOLED_EVENTS)"   # False = 开关默认关
  3. sweep 每一轮做什么（srvbench.py ... sweep）：起 4 个 rank 进程（每张卡注册 MiniMax-M3 形状的 page view）和 1 个 scheduler 进程，只用一个会话；第 t 轮 prompt 长度 P = t × 16k：lookup(P) → 4 个 rank 各自 retrieve [0, P − 16k) → 4 个 rank 各自 store 新增的 [P − 16k, P) → end_session。SB_T_SWEEP=32 时 P 从 16k 到 524,288。整套跑两遍（pass0 预热、pass1 测量），每遍用新的随机 token，只统计 pass1。
  4. 运行：6 组按上面的命令交替各跑 2 轮（每组约 5 分钟，含启动时锁 800 GB L1 约 2 分钟），sweep 之后脚本接着跑同时到达的 burst。
  5. 检查这一轮有没有被干扰：server.log 里 0 条 triggering eviction、0 条 Expanded（L1 没扩容）、0 条 Reaped GPU instance；summary.json 里 burst retrieve 次数 = 144、失败操作 = 0。有一项不满足就重跑这一轮。
  6. 出曲线：sweep.json 的每条记录是 [kind, prompt_tokens, seconds, tag]，kind 有 lookup / retrieve / store / turn（一整轮）以及 *_rank_max、*_submit。sweep_curves.py 取 pass1、按 prompt 长度对各轮求均值，输出 sweep_curves.json / .csv，第 8.2 节的三张图就是用它画的。 
    python sweep_curves.py runs stock pool hash fk all3 all4 --kinds retrieve,store,turn
