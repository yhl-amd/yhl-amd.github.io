LMCache MP final optimization: four changes

2026-10-31 · ATOM uses LMCache MP (lmcache_driven mode) for KV offload · Code: yhl-amd/LMCache#2 (the three patches, on the LMCache f22dec28 shipped in the ATOM image), #3 (the event pool ported to LMCache dev, with reproduction scripts)

In one sentence: the LMCache server wastes time in four places on every RPC: destroying an event waits for the copy to finish, every request carries the whole token prefix, ObjectKeys are built and validated one by one, and 4 ranks share 1 thread in one queue. Each of the four changes removes one of them, with no overlap.

1. Overview: stock vs all four changes

Example: a 153,600-token prompt at its last prefill step; 4 ranks send a store at the same time, while another new request sends a lookup. CPU work is drawn at measured scale: decoding a request that carries the whole token prefix 2.4 ms, hashing the whole prompt 2.6 ms, building 2,400 ObjectKeys 1.7 ms (0.44 ms batched), handler about 3 ms; a 383 MB copy is estimated at 20 ms.

Decoding whole token prefixes (holds the GIL) Hashing the whole prompt / building keys one by one Handler work (about 3 ms) Stuck destroying an event, waiting for the copy Queued, GPU idle GPU copy
  • Stock: the ZMQ thread first decodes the whole token prefix of each of the 5 requests, one by one (about 12 ms in total, holding the GIL); the only store/retrieve thread, after handling one rank, is stuck in a destroy until that GPU's copy is done, so the copies of the 4 GPUs run one after another and all finish only after about 94 ms; the lookup thread also re-hashes the whole prompt and builds 2,400 keys one by one.
  • All four: requests carry only chunk hashes, so decoding costs almost nothing (change 2); the lookup thread no longer hashes and builds keys in bulk (changes 2 and 3); 4 threads each own one rank (change 4) and are no longer stuck in destroys (change 1); everything finishes in about 23 ms.

2. Background: what happens in one store / retrieve

ATOM registers its KV cache memory with the LMCache server, and the server reads and writes ATOM's GPU memory directly on its own copy stream. For every store / retrieve:

  1. ATOM sends an RPC carrying the key (in stock, the whole token prefix from token 0), the block IDs and the handle of an interprocess event;
  2. the server decodes the request, computes each chunk's hash from the tokens, builds ObjectKeys, and allocates or looks them up in L1;
  3. the server orders its work after ATOM's on the GPU with two interprocess events (table below), queues the copy and replies.
① Producer event (ATOM → server)② Completion event (server → ATOM)
Meaning“The KV is written, copy it”“The copy is done: the blocks can be freed / the request can run”

3. Change 1: IPC event reuse (event pool)

3.1 Problem: destroying an event blocks the thread

  • On ROCm 7.2.x, destroying an interprocess event goes through ~IPCEvent → ihipHostUnregister → SyncAllStreams and returns only after all the work this process has queued on that GPU is done (rocm-systems#7520; fixed in develop by #7710, the 7.2 backport #11529 is not merged).
  • While it waits, other threads that create an interprocess event are blocked too (measured: 43 µs → 38.6 ms).
  • Stock creates, imports and destroys events on every store/retrieve, so every operation blocks once. LMCache dev's #5439 moved the destroy to another thread, but every operation still destroys an event.

The blocked time is spent waiting for the copy, not on the destroy itself:

  • Why it is safe: record moves an event to a new position, and wait/query always see the latest one; if an event is re-recorded early, the other side only sees a later position on the same stream: it may wait longer, but is never released early. Two processes reusing events for 400 rounds: 0 early releases, 0 false completions.
  • No leak: for the same data written, stock and the event pool use the same L1 memory (485 GB vs 484 GB after 80k chunks).

4. Change 2: token hashing moves to the client, no more whole token prefixes

The key of a KV chunk is a chained hash: hk = blake3(hk−1 ‖ the 256 tokens of chunk k), so every chunk's key depends on all the tokens before it. The stock protocol lets only the server compute hashes, so ATOM sends the whole prefix from token 0 every time in lookup, store, retrieve and free_lookup_locks, from every rank, and requests grow with the prefix; the server decodes them on the ZMQ thread while holding the GIL, copies them into the session, and hashes them. With the change, the client computes chunk hashes incrementally per request and an RPC carries only the hashes of its range.

Figure ②-1: what one store request carries; stock sends all tokens, the change sends only chunk hashes

The example is the round in the figure below: rank 2 stores chunks 536–599 computed in this round (tokens 137,216–153,599). Chunk hashes are chained: hk = blake3(hk−1 ‖ the 256 tokens of chunk k), with none_hash before h0, so every chunk's key depends on all the tokens before it. The stock protocol lets only the server hash, so the client always starts from token 0; when the server's session has cached earlier hashes it hashes only the new chunks, but the tokens are still sent, decoded and copied into the session in full. With the change, the client adapter caches the hashes it has computed per request and hashes only the new chunks each step, byte-identical to the server's TokenHasher (tested); ATOM's load and save are both 256-aligned and always extend an existing prefix, so a range can be described entirely by the hashes of its chunks.

Example: one round of a multi-turn conversation with a prompt of 153,600 tokens (600 chunks of 256 tokens). The first 100,352 tokens are still in the GPU prefix cache, LMCache hits up to 137,216, and the last 16,384 are new tokens prefilled in one step. Which tokens each RPC carries comes from the ATOM code: lookup and free_lookup_locks carry the whole prompt (_lookup_token_ids()), retrieve carries token_ids[:transfer_end], store carries token_ids[:aligned], end_session only request_id; retrieve and store are sent once by each of the 4 ranks. Byte counts were measured on the real prompts of this benchmark: the aiperf dataset tokenized with M3's chat template takes 2.78 B per token on average in msgpack (8% of the ids are ≥ 65,536 and take 5 B); decoding 153,600 tokens measured 2.2–2.5 ms, drawn at 2.35 ms. With the change each chunk hash is 32 B, and a key with hashes decodes in a measured 0.7–0.8 µs (mm3/micro_hashkey.py). The number of chunks the stock server hashes is derived from the code: lookup hashes the whole prompt from the start with compute_chunk_hashes, free_lookup_locks also hashes from chunk 0 to end, and retrieve and store hash incrementally through the session, which the 4 ranks share. Notes and cost

  • The ATOM-side adapter uses exactly the server's TokenHasher rule (blake3, 256 tokens per chunk) and hashes incrementally per request, byte-identical (tested); ATOM's load and save are both 256-aligned, so a range can be described entirely by the hashes of its chunks.
  • The server no longer decodes, copies or hashes tokens. In the real service, lookup execution went from 51.4 to 23.7 ms and GIL-holding samples on the ZMQ receive thread from 683 to 18.
  • The cost moves to the client: the first operation of a new request hashes the whole prompt on the calling thread (about 4.7 ms for 128k), then about 0.2 ms per additional 16k. It would be better for the scheduler to hash once at lookup time and pass the hashes to the workers.
  • Client and server hashing rules are now coupled; the server checks the algorithm and rejects a mismatch.

5. Change 3: batched ObjectKey construction

A lookup of a 153,600-token (600-chunk) prompt under TP4 builds 2,400 ObjectKeys (600 chunks × 4 ranks). Each goes through a frozen dataclass __init__, and __post_init__ checks whether the model name contains @, whether the group is negative, and whether the salt has forbidden characters or is too long — all 2,400 checks are on the same model name and the same salt. free_lookup_locks and end_session do it all again.

Time to build 2,400 ObjectKeys (ms)
The change
  • Fields shared by one call (model name, group, salt) are validated once, then filled in bulk, without calling the dataclass constructor for each key.
  • Keys built in bulk equal the dataclass-built ones and hash the same (unit tests).
  • On its own the gain is small (lookup execution about −7%), but together with change 2 it brings down the CPU time of lookup / free_lookup_locks / end_session.

6. Change 4: --max-gpu-workers 4

6.1 Problem: 4 ranks in one queue

The LMCache server handles store/retrieve with --max-gpu-workers threads, 1 by default. Each rank gets a thread on its first request, and all its later requests go to that thread in order. ATOM TP4 has 4 ranks and there is only 1 thread, so they all share it. The server log says so:

LMCache WARNING: AffinityThreadPool: affinity_key=... wrapped onto worker slot 0 (only 1 workers),
    so it shares a thread with an earlier key and their tasks are serialized.

In the real service's server trace, retrieve queues on the server for a median of 0.65–0.86 s, while it executes in only 18 ms.

6.2 The fix, and why it goes with the event pool

  • Set the thread count to the number of ranks (4 for TP4): one thread per rank, so the 4 GPUs' requests are handled in parallel. Requests of the same rank are still handled one after another, so more threads do not help; when several ATOM instances share one server, set it to the total number of clients.
  • With 4 threads alone, each thread still “does one job, then waits” (stuck in the destroy); with the event pool it takes the next job right away. Below: all 4 threads on, and the same rank sends 3 requests in a row:
Thread handling a request (about 3 ms) Thread stuck destroying an event until this GPU's copy is done GPU copy (about 20 ms) ATOM learns “copy done”

7. Companion fix: avoiding a GPU hang with mono

In one sentence: on ROCm 7.2, the server's GPU-side wait on ATOM's IPC event (①) actually launches a polling kernel with a single thread. ATOM's mono kernels need all 256 CTAs co-resident (one per CU) and spin-wait on each other. If the polling kernel takes a CU's slot first, that mono CTA cannot get in, while the signal the polling kernel waits for is only written after mono finishes — each waits for the other and the GPU hangs. The fix: never wait on the GPU for an event that has not fired.

7.1 Why it hangs

  • A ROCm 7.2 IPC event is a signal slot in shared memory. The server's stream.wait_event → ROCCLR_COMMAND_STREAM_WAIT_VALUE; by default (GPU_STREAMOPS_CP_WAIT=false) rocclr runs a one-work-item blit kernel, streamOpsWait, that keeps reading that memory until the value becomes 0.
  • ATOM mono (ATOM_MONO_ENABLE is on by default; DSV4, GLM-5.2 and MiniMax-M3 all have it): mono/config.py says “one CTA per CU, all co-resident”; the CTAs spin-wait on each other, which relies on all of them being on the GPU at once.
  • The server and ATOM run on the same GPU. ATOM usually sends a request before ① has fired; if the server's polling kernel gets onto the GPU first and takes a CU's slot, a mono kernel dispatched after it has one CTA that cannot get in.
Mono CTAs (one per CU, spin-waiting on each other) Server polling kernel (waiting for ①) Cannot get in / waiting Server copy Server CPU work

7.2 The fix: two layers, both off by default

SwitchWhereWhat it does
LMCACHE_MP_SUBMIT_AFTER_PRODUCER=1Client (ATOM adapter)Store/retrieve requests are handed to a background thread, which polls ① on the CPU (query() only reads host memory) and sends each request once ① has fired; submit returns a future at once that reports not-done until then. ATOM's calling thread never blocks.
LMCACHE_MP_HOST_WAIT_PRODUCER=1serverChecks ① on the CPU first: if it has fired, no GPU wait is queued; if not (an old client sent early), it polls on the CPU and never queues a polling kernel on the GPU.
  • The remaining server kernels (the copy, and the signal write that records ②) do not depend on mono and finish on their own; at most they delay mono's start a little, with no circular wait. ATOM only query()s ② on the CPU.
  • Correctness: ROCm 7.2 issues a release barrier before writing the signal, so when the CPU sees ① fired, ATOM's KV writes are already visible and the copy queued afterwards is correctly ordered.
  • The root fix is in ROCm: develop has merged #5575, which uses ROCr IPC signals waited on by the CP, with no polling kernel; it is not in 7.2 yet.

9. How to use

# ATOM (LMCache client) side
export LMCACHE_MP_POOLED_EVENTS=1   # change 1: event pool
export LMCACHE_MP_CLIENT_HASH=1     # change 2: client chunk hashing (needs a blake3 server)

# LMCache server side
export LMCACHE_MP_FAST_KEYS=1       # change 3: batched ObjectKey construction
lmcache server ... --max-gpu-workers 4   # change 4: one thread per rank (TP4 → 4)

# Companion fix: required with mono (avoids GPU hangs)
export LMCACHE_MP_SUBMIT_AFTER_PRODUCER=1   # client: send after ① has fired
export LMCACHE_MP_HOST_WAIT_PRODUCER=1      # server: never wait on the GPU for an unfinished ①
  • The first three are off by default and must be turned on; the new fields all have defaults, so old and new clients and servers interoperate.
  • Code: all three are in #2 (f22dec28); the event pool is ported to dev in #3.
  • Give L1 headroom: faster handling means more writes in flight; L1 grows lazily by default, and when growth lags behind it triggers eviction early. --l1-init-size-gb grows it enough at startup.

10. Caveats

  • Turn on the companion fix with mono (section 7): otherwise, on ROCm 7.2, the server's polling kernel can deadlock with mono and hang the GPU.
  • L1 growth blocks HIP calls: L1 grows lazily by default, pinning 10 GB at a time with hipHostRegister; for the few seconds of each pin, the server's IPC event records and the IPC handle opens at registration are blocked, showing up as ~10 s stalls, registration timeouts and instances reaped by the server (Reaped GPU instance). In production, either grow L1 enough at startup with --l1-init-size-gb or accept occasional stalls.
  • Heartbeat / registration stalls: ATOM's docs currently say not to raise the GPU worker count (per-thread lazy initialization once stalled the server past the client heartbeat). In our benchmarks registration stalls happened with both 1 and 4 threads, and the trigger is not understood; before going to production, check the server log for Reaped GPU instance and registration timeouts.
  • The event pool matters on ROCm: on CUDA destroying an event does not synchronize, so the gain is much smaller; once the ROCm 7.2 backport (#11529) lands, the destroy stall itself goes away.
  • Token hashing moves the hashing cost onto the client's calling thread (about 4.7 ms for a new 128k request); better to hash once in the scheduler and pass the hashes down.
  • Real-service TTFT mean and p99 vary a lot, so per-change end-to-end numbers are indicative only; server-side metrics change by large factors and repeat well.

What each sweep turn does (srvbench.py ... sweep): start 4 rank processes (each registers MiniMax-M3-shaped page views on its GPU) and 1 scheduler process, with a single conversation; turn t has prompt length P = t × 16k: lookup(P) → each of the 4 ranks retrieves [0, P − 16k) → each of the 4 ranks stores the new [P − 16k, P) → end_session. With SB_T_SWEEP=32, P goes from 16k to 524,288. The whole sweep runs twice (pass0 warm-up, pass1 measured) with fresh random tokens each pass; only pass1 counts.
  4. Run: run the 6 arms with the commands above, 2 rounds each, interleaved (about 5 minutes per arm, including about 2 minutes to pin 800 GB of L1 at startup); after the sweep the script runs the bursts.
  5. Check that a run was not disturbed: server.log has 0 lines of triggering eviction, 0 of Expanded (L1 did not grow) and 0 of Reaped GPU instance; summary.json shows 144 burst retrieves and 0 failed ops. If any check fails, rerun that round.
  6. Curves: each record in sweep.json is [kind, prompt_tokens, seconds, tag], with kinds lookup / retrieve / store / turn (a whole turn) plus *_rank_max and *_submit. sweep_curves.py takes pass1, averages each prompt length over the rounds, and writes sweep_curves.json / .csv; the three charts in section 8.2 are drawn from it.

When benchmarking: ① pin all of L1 at startup and never grow it during the run (SB_L1 = SB_L1_INIT, larger than the total data written), otherwise pinning stalls the server for seconds and can even time out registration and get instances reaped; ② check that each run's server.log has no triggering eviction or Reaped GPU instance, and that summary.json shows 144 burst retrieves; ③ ports 5566 and 9090 may be taken by other services on the host, so the script defaults to 15566 and 19788.
