DeepSeek-V4.1-Flash · 相对 V4 的变化

DeepSeek-V4.1-Flash 图解

V4.1-Flash 是 DeepSeek 新架构家族里最小的模型，从头训练，不是 V4 的微调。它要解决的是 agent 场景的成本问题：输入远比输出多，prefill 算力和 KV cache 的存储都很贵。为此它把 prefill 的层数砍掉一半，HBM 里的 KV 压到约 1/4，落盘的 KV 压到约 1/8。

来源：技术报告 arXiv 2609.19969、HF 仓库里的 config.json 和官方参考代码 inference/model.py、vLLM 部署博客。标“推算”的数字是我按 config 算的，论文里没有直接给出。

890 B每 token 全局 KV，约 V4-Flash 的 1/4
≈ 1/8落盘（SSD / host）的持久 KV，相对 V4-Flash
8B / 16B每 token 激活参数：prefill / decode
4 / 40真正产出全局 KV 的层数
第一部分

概览：V4.1 是什么，改了什么

先建立整体印象。看完这一部分，你应该能用三句话向别人讲清 V4.1 相对 V4 的变化。

1.1

V4.1-Flash 是什么

  • 原生多模态 MoE：输入图和文本，输出文本。主干 552B 参数，另有 196B 的 Engram 查表参数，激活参数 prefill 时 8B、decode 时 16B。
  • 40 层：前 20 层叫因果编码器，后 20 层叫解码器（CED，见 2.1）。hidden size 5120，上下文 1M。
  • 从头训练：45T token 的图文语料，稀疏注意力在 64K 长度上训练，34T token 时扩到 1M。后训练仍是 SFT → RL → OPD。
  • 推理强度可以设成 1–100 之间的任意整数，取代 V4 的固定三档。
  • MIT 协议开源。API 名称为 deepseek-flash，V4-Flash 已下线并临时转发到 V4.1-Flash。

没变的部分

单层 attention 的“内核”几乎原样保留：

  • shared-KV MQA：1 个 KV head，head_dim 512，同一份 KV 既当 K 又当 V；
  • partial RoPE（最后 64 维）和输出端 inverse RoPE；
  • attn_sink，以及 SWA 与压缩 KV 在同一次 softmax 里竞争；
  • grouped output projection（8 组 × 1024）、SWA 窗口 128、前 2 层纯 SWA；
  • indexer 的 ReLU 加权打分和 FP4 量化，top-k 512；
  • MoE 的 sqrtsoftplus 打分、noaux_tc 均衡、1 个共享 + 6 个激活专家、专家权重 FP4；
  • 1M 上下文的 YaRN 设置（factor 16、原始长度 65536）。
1.3

为什么这么改：三条主线

论文的出发点是 agent 负载：频繁的工具调用会带来大量 prefill，KV cache 一旦没命中，重算代价很高；长上下文又让 HBM 和 SSD 的容量、带宽都吃紧。所有改动都能归到下面三条线上：

要省的东西主要手段效果
prefill 算力CED：prompt 的大部分 token 只跑前 20 层prefill 激活 8B，约为 decode 的一半
HBM 里的全局 KVCSA2 跨层共享（40 层里只有 4 层存 KV）+ FP4890 B/token，约 1/4
SSD 上的持久 KVSWA 不落盘，靠 Bounded Replay 近似重建约 1/8

另外还有三个“顺手的效率扩展”：Single-Pass mHC 把残差混合的访存减半；Engram 用便宜的查表换一部分容量；DSpark 用更强的投机解码提升 decode 速度。

第二部分

重点：七个改动，各用一张图看懂

每节讲清“做了什么、为什么省”，配一个小例子。细节放到第三部分。

2.1

CED：prompt 只需走完前 20 层

一句话：后 20 层（解码器）回头看历史时用的全局 KV，统一由前 20 层（编码器）的输出投影得到。所以 prompt 的绝大部分 token 只要算完前 20 层，解码器只补算最后 128 个。模型仍是一条序列、一个 40 层的因果模型，decode 时每个新 token 照样走完 40 层；“编码器 / 解码器”只是前 20 层和后 20 层的名字。

切成两半，只改了一件事

每一层回头看历史 token 时，读的是这些 token 在本层留下的笔记（KV）。在普通的 decoder-only 模型里，token t 在第 l 层的笔记由它在第 l 层的隐状态算出来，所以要让 40 层都有笔记，prompt 的每个 token 都必须走完 40 层。

V4.1 的每一层要读两种笔记：覆盖全部历史的全局 KV，和只覆盖最近 128 个 token 的 SWA KV。CED 只改了前一种：解码器的全局笔记不再由各层自己写，而是由 L20 根据 H20（编码器 L0–19 的输出）给每个 token 写一份 KV④，L20–39 共用。SWA KV 仍然每层用自己的隐状态算。（这和 2.2 节“组长写笔记、组员共用”是同一个思路：L20 就是整个解码器的组长。）

严格来说，最后 128 个 token 在 L30 的 SWA KV 依赖它们在 L29 的结果，而后者又依赖更早的 token，精确计算要往前追 20 × 128 = 2560 个 token。V4.1 只补算最后 128 个，并把窗口截断在这里（Decoder SWA Bounded Replay，见 3.2）。

一共四份全局 KV，各由一层写

KV④ 不是唯一的全局 KV。除了只有 SWA 的 L0、L1，每一层都要读一份全局 KV，但不是每层自己写：相邻几层编成一组，由组里第一层写一份，全组共用（这就是 2.2 节的 CSA2）。整个模型一共只有 4 份：

  • m 是压缩率：每 m 个相邻 token 合成一个 entry。编码器的三份 m=2，所以 entry 数是 token 数的一半；KV④ 的 m=1，一个 token 一个 entry。
  • 四份互相独立：每份都由写它的那一层用自己的权重、从自己的输入算出来。KV④ 不是从 ①②③ 转换来的，L20 也不需要重算编码器的 KV，各写各的。
  • 每 token 的字节数：每个 entry 都是 356 B，组成见 3.5 节。m=2 时两个 token 分摊一个 entry，每 token 178 B；m=1 时每 token 356 B。四份加起来是 3 × 178 + 356 = 890 B/token。

KV④ 很便宜：每个 token 只做一次投影，不需要 attention，也不需要 MoE。L20 的压缩器在 m=1 时就是：

if ratio == 1:
    return self.norm(self.wkv(x))   # 5120 → 512，再 RMSNorm；之后加 RoPE、量化成 FP4

另外再投影一次得到 indexer K（512 → 128）。所以 prompt 里每个 token 的成本是：编码器 20 层整层计算 + KV④ 一次投影；解码器 20 层（包括 L20 的 attention 和 MoE）只算最后 128 个 token。论文的说法也是这个意思：只算前一半层，就能以很小的代价拿到上半部分的全局 KV。

vLLM 和 ATOM 现在都这样实现：L20 只给全部 token 写 KV④，L20 的 attention、MoE 和 L21–39 一样只跑最后 128 个。vLLM 是在 10/09 的 #59894 里改成这样的，之前 L20 整层要跑全部 token。

例子：用“层数 × token 数”粗略衡量 prefill 计算量：

prompt 长度不用 CED（40 层 × N）CED（20 层 × N + 20 层 × 128）比例
1K40,96023,04056%

2.2

CSA2：一份 KV，多层共用

一句话：相邻几层编成一组，组长负责写笔记、挑重点，组员直接用组长的成果，只做自己的那份阅读。要理解这句话，先看 V4 里每一层在做什么。

先看 V4：每一层都要做三件事

模型生成下一个 token 时，每一层都要回头看前面所有 token，从中找有用的信息。可以这样想：每个历史 token 在每一层都留下一条笔记（就是 KV），每一层有自己的一本笔记本（这一层的 KV cache）。上下文有 100 万个 token 时，笔记太多，不可能每条都细看，所以 V4 的每个 CSA 层都分三步：

步骤做什么术语
① 写笔记把历史 token 压缩成笔记，存进本层的笔记本压缩 KV、KV cache
② 挑笔记用一个便宜的打分器给所有笔记快速打分，挑出最相关的 512 条indexer、top-k
③ 读笔记带着本层自己的问题，仔细读这 512 条，得出结论attention，用本层的 Q

V4 里每个 CSA 层都把这三步完整做一遍。

V4.1 的想法：组长做①②，组员只做③

相邻几层写出来的笔记很像，挑出来的 512 个位置也很像，每层各做一遍是重复劳动。于是 V4.1 把相邻的层编成一组。三种模式的区别，就是各自做了哪几步：

模式① 写笔记② 挑笔记③ 读笔记
Full（组长）自己写自己挑自己读
Reindex用组长的笔记自己重新挑自己读
Reuse用组长的笔记用别人挑好的自己读

所以 Reuse 就是只做第③步的层：笔记本是别人的，读哪 512 条也是别人定的，它只负责带着自己的问题去读。40 层里有 30 层是 Reuse。

例子：编码器第 2–7 层处理 token #2000

  1. 第 2 层（Full，组长）：把历史 token 压缩成笔记存起来；打分后挑出 512 个位置，比如 {15, 230, 871, …}；再带着自己的问题读这 512 条。
  2. 第 3 层（Reuse）：不写笔记，也不打分。直接翻开第 2 层的笔记本，读 {15, 230, 871, …} 这 512 条。它带的是自己的问题（自己的 Q），所以读出来的结论和第 2 层不一样。
  3. 第 4–7 层：和第 3 层一样。

打个比方：6 个人的学习小组

V4 的做法

6 个人复习一本超厚的教材。每个人各自把整本书做一遍摘要，再各自翻摘要找出 512 页重点。

6 份摘要，6 次查找
V4.1 的做法

组长做摘要，并标出 512 页重点。其余 5 人直接读这 512 页，各自带着自己的问题去读，得到各自的答案。

1 份摘要，1 次查找
  • 省了显存：只存 1 份笔记。30 个 Reuse 层都不存笔记，这是全局 KV cache 能小到 890 B/token 的主要原因。
  • 省了计算：只查找 1 次，indexer 的打分和排序都省掉了。
  • 代价：如果第 5 个人真正需要的那一页组长没标出来，他就看不到。这就是 Reuse 的近似：默认相邻几层关心的位置差不多。
补充两点容易漏掉

最近 128 个 token 每层仍然自己看。这是 SWA 旁支，很便宜，Reuse 层也照样自己算。所以 Reuse 层其实读两样东西：组长那 512 条笔记，加上自己的最近 128 个 token，两者放在同一次 softmax 里。

解码器稍微复杂一点。它的笔记全部由第 20 层写；但每 4 层会有一层（第 24、28、32、36 层）是 Reindex，用第 20 层的笔记重新挑一次 512 个位置，紧跟其后的 3 层 Reuse 就用这次新挑的结果。

2.3

压缩变简单了：不重叠、无位置偏置、解码器不压缩

代价从哪里补回来？编码器 m=2 比 V4 的 m=4 保留了更多细节；解码器 m=1 等于完全不压缩。由于 40 层里只有 4 层存 KV，即使压缩率更低，总 KV 仍然小得多。论文没有解释为什么选 m=2 和 m=1。

2.4

分层 indexer：先粗选块，再细选位置

解码器 m=1，1M 上下文就有 1M 个候选位置。如果 5 个打分层（第 20、24、28、32、36 层）都全扫一遍，indexer 的成本会很高。V4.1 让第 20 层全扫一次并圈出一个候选池，后面的 Reindex 层只在池子里打分。

1,048,576 个位置第 20 层 indexer 全扫 → 自己的 top-512同时按块取最高分 → 2048 块 × 8 = 16,384 个候选第 24/28/32/36 层只扫候选 → 各自的 top-512

例子：1M 上下文时，每个 Reindex 层的打分量从 1,048,576 降到 16,384，减少到 1/64，而且不再随上下文变长而增长。代价是近似：某个 Reindex 层真正想看的位置，如果不在第 20 层圈出的块里，就会被漏掉。第三部分有可以拖动的例子。这个机制只用在解码器，而且是 post-training 阶段才加入的，训练和推理都受同样的限制。

2.5

FP4 主 KV：每个 entry 从 576 B 到 288 B

V4 的主 KV 是 448 维 FP8 + 64 维 BF16（≈576 B/entry）。V4.1 把 512 维全部存成 FP4，每 16 个通道配一个 E4M3 scale（256 + 32 = 288 B/entry）。RoPE 维度也一样，在 RoPE 之后再量化。SWA KV 仍是 FP8。

例子：一个 1M token 的会话，全局 KV 约 0.9 GB；V4-Flash 约 3.5 GB。SWA 部分固定为 40 层 × 128 个 token，约 2.7 MB，与上下文长度无关（推算）。

2.6

SWA Bounded Replay：SWA 不落盘，丢了只补 128 个 token

全局 KV 只依赖 token 本身，可以存到 SSD，下一轮直接读回。SWA KV 却是每层各算一份、依赖层内隐状态的，要精确恢复，得重算 层数 × 128 个 token。V4.1 的做法是：只重放最后 128 个 token，窗口在重放起点截断。结果是近似的，但便宜得多。为什么精确恢复要重算这么多，3.6 节有逐步图解。

  • HBM：运行中的全局 KV。SSD / host：持久化的全局 KV，至少保留 72 小时。
  • 编码器 SWA KV：放在分布式内存池里（每台机器拿 10% 的 host DRAM），TTL 只有几分钟。几分钟内的下一轮可以直接命中，过期就靠 replay 重建。
  • 解码器 SWA KV：从不缓存，每次 prefill 都在最后 128 个 token 上重建，这一步正好和 CED 的设计衔接。
  • 持久 KV 能降到约 1/8，原因有两个：全局 KV 本身只有约 1/4，而 SWA 又不再落盘。
2.7

另外三个扩展：mHC、Engram、DSpark

Single-Pass mHC

V4 每层要先读一遍残差流来算混合系数，再读一遍去用它。V4.1 改成用上一层算好的系数，读一遍就够了。

V4 : F_l(A_l · X_l)
V4.1 : F_l(A_(l−1) · X_l)
访存 (4n+4)d → (2n+2)d，减半
Engram

用前 2–4 个 token 组成 n-gram，哈希后去一张巨大的表里取向量，加回隐状态。196B 参数，只放在第 1 层和第 14 层。

“the cat sat” → 哈希 (cat, sat)、(the, cat, sat)…
→ 查表 → 门控 → 加到 h
表放在 host 内存，通过 RDMA 预取
DSpark

取代 MTP 的投机解码头。3 个小 Transformer block 读取第 37–39 层的隐状态，一次前向并行草拟 5 个位置，再由主模型验证。

Markov 头：建模相邻草稿之间的依赖
置信度头：预测每个位置被接受的概率
→ 按请求动态决定验证长度

为什么解码器只算 128 个 token 就够

decode 的第一步，解码器各层需要 prompt 最后 128 个 token 在本层的 SWA KV。要精确算出来，得从更早的 token 开始逐层往下追：论文的说法是要让 20 个解码器层跑 20 × 128 = 2560 个 token。论文引用的先前工作指出，SWA 实际的有效感受野比理论值小得多，所以 V4.1 只重放最后 128 个，并把窗口截断在重放起点（Decoder SWA Bounded Replay）。结果不是数学上严格相等的，论文说对回答质量的影响可以忽略，还在 post-training 中模拟了同样的重放，让模型提前适应。

注意近似的一个副作用

场景 (c) 中，新增后缀的全局 KV 和 SWA KV 依赖于“缓存从哪个位置命中”：同一段文字在不同命中位置下，算出来的 KV 不完全相同。论文说这几乎不影响回答质量。

官方参考代码 model.py 不做跳层，每个 Block 处理每个 token。跳层在生产推理系统里实现，vLLM 的做法是把一个 step 拆成两段：编码器和 L20 的 KV 写入用完整 batch，L20 其余部分和 L21–39 用只含最后 128 行的裁剪 batch（10/09 的 #59894 之前是层 0–20 用完整 batch），开关 --[no-]swa-bounded-replay 默认打开，带 CUDA graph 时 prefill 耗时下降 30–40%。

先理解论文说的“三个乘法维度”

维度怎么省已有做法
每个 entry 的大小减少 KV head，或多个 head 共享一个 latentGQA、MLA；V4/V4.1 的 shared-KV（1 个 KV head）

分层 indexer 与 decode 成本：论文图 5、图 2

论文图 5 用方格表示位置：L20 在全部位置上打分，按块取最高分圈出候选块（图中的蓝框），后面的 Reindex 层只在这些块里打分。论文图 2 显示 V4.1 的 decode 算力几乎不随上下文增长。这两张图讲的其实是同一件事。

候选池怎么建（select_candidate_blocks）

  1. L20 给全部可见位置打分，先选出自己用的 top-512；
  2. 把位置按 8 个一块切开，每块取块内最高分作为块分（不足一块的用 −inf 补齐）；
  3. 最新的那一块（可能还没填满）强制入选；
  4. 取块分最高的 2048 块，共 16,384 个位置，展开成逐位置的掩码，写进 shared_attn.candidates；
  5. Reindex 层打分时把池外位置置为 −inf：index_score.masked_fill(~shared_attn.candidates, -torch.inf)，再各自取 top-512。

为什么 decode 算力几乎不随上下文涨（论文图 2）

每生成一个 token 的成本随上下文长度 N 怎么变
MoE 和各种投影不变

粗算（推算）：每打分一个位置，32 个 head 各做一次 128 维点积，约 32 × 256 FLOPs；论文图 2 把 FP4 运算按 0.25 计权。从 4K 到 1M，4 个 Full 层多打分约 266 万个位置，约合 266 万 × 32 × 256 × 0.25 ≈ 5.4 GFLOPs。从论文图 2 读出 V4.1 的曲线大约从 20 涨到 25–26 GFLOPs，与论文说的“上下文扩大 256 倍，decode 算力只增加 1/4”吻合。所以 V4.1 decode 成本里随上下文增长的，几乎只有这 4 个 Full 层的全扫。

vLLM 的实测（DeepGEMM 的 sparse MQA logits kernel，GB300）：单个 Reindex 层在 8K 上下文时快 1.2×，512K 时快 14–23×；端到端 prefill 在 512K 时快 1.43×，1M 时快 2×。

FP4 KV 与 890 B：论文图 1b

论文图 1b 列出四代模型每 token 的全局 KV。下面先按对数刻度画出这组数，再把 890 B 拆到每一个字节。

一个 entry 的位布局（论文只有文字）

  • 没有第二级全局 scale：E4M3 最大 448，E2M1 最大 6，可表示到 448 × 6 = 2688。论文的论证是：训练出的 RMSNorm 权重最大约为 1，归一化后 512 维 latent 的长度最多约 √512；RoPE 是旋转，不改变长度，所以任何一个通道的绝对值都不超过 √512 ≈ 22.6，训练中实测最大约 10，远低于上限。
  • RoPE 之后再量化：NoPE 和 RoPE 维度用同一格式。论文试过 RoPE 之前量化，精度只略好一点，却会给 decode 增加额外开销。
  • SWA KV 仍是 FP8：它对量化更敏感。
  • 主 KV 的 FP4 只省存储，不省计算：attention 之前先反量化，所以可以选精度更高的 NVFP4 式格式，不要求硬件支持 FP4 矩阵乘。indexer 的 Q/K 则用 OCP 标准的 MXFP4，这是为了兼容尽可能多的硬件平台，因为 indexer 要直接用 FP4 做矩阵乘。
  • QAT 在 post-training 阶段引入。相比 V4 的 FP8 主 KV，存储在 HBM 和 SSD 上都接近减半。

3.6

SWA 的依赖链与 Bounded Replay

这一节回答两个问题：SWA 缓存丢了以后，为什么要重算那么多 token？ V4.1 的 Bounded Replay 又是怎么把这个代价压下来的？为了画得清楚，示意图里把窗口从 128 缩成 4。

第一步：每一层都有自己的“最近 128 条笔记”

SWA 的意思是：每个 token 只看最近的 128 个 token，含它自己。为此每一层都维护一个环形缓冲，里面放着最近 128 个 token 在这一层的 KV，下面叫“笔记”。L0 有 L0 的笔记，L1 有 L1 的笔记，互不相通。

关键在于笔记是怎么来的。token s 在第 l 层的笔记，是用 token s 进入第 l 层时的隐状态投影出来的（3.3 节代码里的 kv_norm(wkv(x))）。而 token s 进入第 l 层时的隐状态，就是它从第 l−1 层出来时的输出。

所以：想要第 l 层的笔记，得先有第 l−1 层的输出；而第 l−1 层要算出输出，又得先在第 l−1 层做一次 attention，去看第 l−1 层的笔记。依赖就这样一层一层往下传。

第二步：只看两层，L1 就要用到 L0 的 7 个 token

窗口取 4，算 token 12 在 L1 的 attention。图中箭头的意思是“需要”，从上往下读：

  1. token 12 在 L1 做 attention，要看 L1 里 token 9、10、11、12 的笔记（窗口 4，含自己）。
  2. 这 4 条笔记，分别由 token 9–12 进入 L1 时的隐状态投影而来。
  3. token 9–12 进入 L1 时的隐状态，就是它们在 L0 的输出。要得到这 4 个输出，L0 必须给 token 9、10、11、12 各做一次 attention。
  4. L0 里，token 9 要看 6–9，token 10 要看 7–10，token 11 要看 8–11，token 12 要看 9–12。
  5. 合起来，L0 需要 token 6 到 12 的笔记，一共 7 个 token。

只叠了两层，需要的 token 就从 4 个变成了 7 个（2 × 4 − 1）。换成真实窗口 128，就是 2 × 128 − 1 = 255 个。这就是你问的情况：L1 的 SWA 要 128 个历史 KV，这 128 个 KV 要 L0 输出 128 个 hidden，而这 128 个 hidden 又要 L0 看 255 个 token。

第三步：层数越多，往回追得越远

每往下多走一层，最左边就要再往前推“窗口 − 1”个 token。叠了 n 层 SWA，最底层需要的 token 数是 128 + (n − 1) × 127，约等于 n × 128：

平时为什么不用付这个代价

正常运行时，每个 token 都按顺序经过每一层。它在某层的笔记一算出来，就写进这一层的环形缓冲，一直留到被新 token 挤出窗口。到了 decode，每层的缓冲里已经存着前面 127 个 token 的笔记，新 token 在每层只需算自己这 1 条（网格的情况②）。

换句话说，依赖链要求的那些计算，在这些 token 当初经过各层时就已经做过了。只有缓存丢了、又要接着往下算的时候，才需要把它补回来。

算法和平时完全一样，只是候选变少了。以 h12 的一个 head 为例：

q12     = token 12 的 query（64 个 head，每个 512 维）
score_j = q12 · KV_j / √512              # j 只取窗口里的 token
w       = softmax([score_j …, sink])     # 一次 softmax
o12     = Σ w_j · KV_j                   # KV 同时当 V；sink 没有 V
h12     = o12 → inverse RoPE → 输出投影 → 残差 → MoE

# 举例：精确时 KV9–12 的分数 = [1.0, 0.5, 2.0, 3.0]，sink = 1.0
精确      ：w12 = 0.58，KV9–11 共分到 0.34
Bounded   ：只剩 KV12 和 sink → w12 = 0.88
# 本该给 KV9–11 的那 34% 被挤给了 KV12 和 sink → o12 变了 → h12 ≈

sink 是什么：可以理解成“空注意力”，一个没有 V 的候选。分给 sink 的权重，相当于这部分注意力“不看任何 token”，对输出没有贡献。所以上面例子里，被截掉的 KV9–11 那 34% 权重，一部分挤到了 KV12，一部分变成了“不看”。

真实情况窗口是 128。L0、L1 只有 SWA；从 L2 开始，每个 query 还会看全局 KV 选出的 512 个 entry，它们从缓存精确读回，不受截断影响。

重放起点：编码器在“前缀命中但 SWA 过期”时，s = H − 128；解码器每次 prefill，s = N − 128。

存储分层：SWA 不再落盘

为什么 SWA 不该落盘：全局 KV 的复用是长尾的，几天后还可能被同一个前缀命中；SWA KV 只在一个活跃会话的几分钟内有用，会话结束或进入下一轮就失效了。把它放进“保留 72 小时”的 SSD 缓存，访问模式和保留策略不匹配。有了 Bounded Replay，SWA 未命中从“灾难性的重算”变成了“便宜的轻微降级”，所以才敢把它从持久缓存里拿掉。

最后算账：SWA 不再落盘，持久化体积约减半；全局 KV 本身约是 V4 的 1/4。两者相乘，持久化 KV 约为 V4-Flash 的 1/8。

3.7

Single-Pass mHC（论文 2.4.1 节，没有图）

mHC 把残差流扩成 n = 4 份，每份 d = 5120 维。每个 token 在每层有三个小矩阵：A 把 4 份混成 1 份作为层的输入，C 把层的输出分发回 4 份，B 让 4 份之间互相混合。

X_l ∈ R^{n×d},   A_l ∈ R^{1×n},   B_l ∈ R^{n×n},   C_l ∈ R^{n×1}         # 都是逐 token 的系数

V4   : X_{l+1} = B_l X_l + C_l F_l( A_l     X_l ),   (A_l, B_l, C_l) = H(X_l)
V4.1 : X_{l+1} = B_l X_l + C_l F_l( A_{l−1} X_l ),   (A_l, B_l, C_l) = H(X_l)

V4 为什么要搬两倍的数据

V4 的实现是三个按顺序执行的 kernel，后一个依赖前一个的结果（下表取 n = 4）：

kernel做什么读
① 残差更新X_l = B_{l−1} X_{l−1} + C_{l−1} Y_{l−1}(n+1)d = 5d
② 预测系数(A_l, B_l, C_l) = H(X_l)，要对整条 Xl 做归约nd = 4d
③ 输入混合X̂_l = A_l X_lnd = 4d
三个 kernel 合计写 (n+1)d = 5d，再加上 F 里 pre-norm 的 2d共 (4n+4)d = 20d

①② 可以合并成一遍：残差更新不需要跨 hidden 维度归约，每算出 Xl 的一小块就能马上累加进系数投影。但 ③ 必须等 Al 出来，而 Al 要等整条 Xl 都归约完，所以只能再读一遍 Xl，最少也要 (3n+2)d。

Single-Pass 的做法：输入混合改用上一个 block 算好的 Al−1，不再依赖本层的归约结果。于是 Xl 的每一块读进来以后，可以同时“用旧系数混合输入”和“累加新系数”。部署用的 Mega-mHC kernel 把残差更新、输入混合、系数预测、pre-norm 和 FP8 转换融成一个 kernel，残差只读一次、写一次，访存减半。论文说这个错位带来的质量损失可以忽略；预训练时仍用多 kernel 实现，因为错位只改变“用哪一层的系数”。

attn_pre, attn_post, attn_comb = self.hc_mixes(x, self.hc_attn_fn, self.hc_attn_scale, self.hc_attn_base)
x = self.hc_pre(x, pre_mix)                        # attention 用的是上一个 FFN 产出的 pre_mix
x = self.hc_post(x, residual, attn_post, attn_comb)
x = self.hc_pre(x, attn_pre)                       # FFN 用 attention 这一步算出的 pre
x = self.hc_post(x, residual, ffn_post, ffn_comb)
return x, ffn_pre                                  # 交给下一个 block 的 attention

参考代码里的错位是按子层（attention / FFN）而不是按整层。第一层用单位混合（make_identity_pre_mix），最后一个 pre_mix 在 norm/head 之前把 4 份流合并。vLLM 的 Mega-mHC 在 GB200 上比 TileLang 路径快 1.14–1.51×。

3.8

Engram

一种“条件记忆”：用 n-gram 的哈希去巨大的嵌入表里取向量。论文的说法是把“记忆”和“计算”解耦。关键性质是寻址是确定性的，只依赖输入 token 序列，所以前向开始之前就能知道要取哪些行，表可以放在 host 内存里提前取。

  • 196B 参数平均分给 2 个模块，位于第 1 层和第 14 层。n-gram 阶数 {2, 3, 4}，每阶 8 个哈希 head、共 2048 维；每个 head 一张约 16M 行的表，表长取互不相同的质数；嵌入表和 K/V 投影都是 FP8。
  • 沿用原版 Engram 的 tokenizer 压缩、多 head 哈希、上下文门控和多分支融合；去掉了短因果卷积，因为收益抵不上它给推理栈带来的复杂度。
token id归一化（NFKC、去重音、小写、合并空白）→ 压缩 id（99,092 种）× 每层每个回看位置一个奇数乘子 → 滚动 XOR第 i 步即 (i+1)-gram → mod 质数 + offset→ 表中的行号
  • 归一化后，“ The”、“the”、“THE” 映射到同一个 id。序列开头或图像 token 处没有足够历史，回看位置被阻断并填 pad。
  • 前向时在 block 之前调用：h = layer.engram(h, engram_hashes[:, :, layer.engram.layer_hash_index, :], engram_mask)。
  • 推理：通过后台 RDMA 从 host 内存预取；第一个模块（L1）的预取和第一个 Transformer block 的计算重叠。取回的 FP8 值和 scale 直接交给后面的 GEMM。RL rollout 时表常驻 GPU，避免 host 内存碎片导致的 OOM。
  • vLLM：异步预取与解码器计算重叠；同一台机器上的多个 DP 副本共享一份 host 表；透明大页让 prefill 查表 kernel 最多快 10×。
3.9

DSpark

  • 结构：3 个 Transformer block（config 中 n_mtp_layers = 3，权重在 mtp.* 下），滑窗 128，MoE 为 128 个专家、激活 3 个。
  • 输入：取主模型 L37、L38、L39 输入处的隐状态（对 4 份 mHC 流取平均）拼起来，经 main_proj / main_norm 投影进 drafter 的窗口 KV。
  • 半自回归草拟：草稿块由已知 token 后接 noise 占位 token（dspark_noise_token_id = 128799）组成，块内不加因果掩码，一次前向并行算出 5 个位置的基础 logits；Markov 头（rank 256）建模相邻草稿之间的依赖。
  • 按置信度调度验证：置信度头预测每个位置被接受的条件概率，由此估计“前 k 个草稿全部存活”的概率；调度器再结合实测的引擎吞吐曲线，在当前负载下为每个请求选择验证长度，目标是整个系统的期望吞吐最大。
  • 训练：V3 的 MTP 是和主干一起预训练的。DSpark 在预训练之后单独训练，主干冻结；post-training 期间继续训练，但梯度不回传到主干。这样它能跟上不断变化的策略，同时加速线上服务和 RL / OPD 的 rollout。

论文正文没有给出接受长度和加速比，vLLM 博客也没有提到 DSpark 的数字。

3.10

MoE 与多模态

  • 规模：384 个 routed 专家（V4-Flash 256 个），中间维 2304（V4-Flash 2048），1 个共享专家，每 token 激活 6 个，route_scale = 1.5，SwiGLU clamp 阈值 10。
  • 没有 hash 路由：config 没有 hash 层字段，model.py 里也没有 hash 路由。
  • 多模态负载均衡：文本和图像 token 各有一套专家 bias（代码里是 bias_vl），各自按自己的负载更新，更新速度 0.001；bias 只决定选哪些专家，不影响加权。另有权重 1e-4 的序列级均衡损失。
  • 视觉：DeepSeek-ViT 从头训练，32 层、hidden 1024、16 head、patch 14，2D-RoPE，3×3 pixel-unshuffle；两层 MLP 投影（hidden 5120）；每张图最多 1024 个 token。图文从预训练第一天起联合训练。
  • 权重量化：dense 部分 FP8，block 从 V4 的 128×128 改为 32×32（ue8m0 scale）；专家权重 FP4。

怎么读

  • 从上往下就是执行顺序：prologue → 编码器 L0–19 → 解码器 L20–39 → epilogue（logits、采样）→ DSpark 写草稿 KV → 3 个草稿块 → 草稿头。

  • 行首色块是层的模式，它决定 attention 半层里有没有压缩器和 indexer：Full 层写 KV 并全扫打分，Reindex 层只在候选池里打分，Reuse 层两样都借。

python3 trace_to_opgraph.py rank0.pt.trace.json.gz \

脚本怎么归类 kernel：

  • 选哪一步：按 CPU 侧的 annotation（--step 是正则）找到这一步发起的所有 launch，再按 correlation id 找对应的 GPU kernel，graph replay 里的 kernel 也算在内。GPU 侧的 annotation 范围不可靠，会漏掉前面的层，所以不用。--all 对所有匹配的步取中位数。
  • 切到层：每遇到一个 mHC 接缝 kernel 就进入下一个半层（第 2n、2n+1 个是 Ln 的 attention 和 FFN，40 层之后是草稿块）。半层的 all-reduce 之后，kernel 归到下一层的层前置、epilogue 或草稿头。
  • 认算子：名字唯一的 kernel 直接按正则归类。名字会重复的几类（FP8 GEMM、BF16 GEMM、RoPE、RMSNorm、all-reduce）按在这一段里出现的次序，对应到这种层模式下同类算子的次序；这个次序由代码固定，跨 stream 交错也不会错位。quantize_fp8 算进紧跟它的那个 FP8 GEMM。PyTorch 小 kernel 和 split-K 归约算进“辅助”，都没对上的算进“未匹配”，加载数据后会出现这两列。
  • 旧 trace：10/23 那份（TP2、BF16 KV、mono decode）也能读，decode 每层只有 mono 的两个大 kernel，未匹配耗时不到 0.1%。
