1. 问题：8 卡同步，每步都等最慢的那张

prefill 是把输入 prompt 过一遍模型、写出 KV cache 的阶段；之后的 decode 一个 token 一个 token 地生成。长 prompt 会被切块，每步每卡最多 prefill --max-num-batched-tokens 个 token（这里是 16k）。

DP attention 下，每一步 8 张卡各算自己的注意力，然后一起进入 MoE 的跨卡通信（megamoe_prepare_compact）。所以这一步多长，取决于最慢的那张卡。

性能采样（两段各约 11 秒的 kernel trace）显示：prefill 占 GPU 时间的 50–60%；卡间注意力代价不均造成的等待约占总 GPU 时间的 6.3%，几乎全部等在 prefill 的 MoE dispatch 上。

2. 代价模型：注意力是个梯形

一段 prefill 从第 start 个 token（前面已缓存）开始，新算 k 个。第 i 个新 token 要看它前面所有 token，平均每个新 token 看 start + k/2 个。

cost(start, k) = k × (W + start + k/2)        W = 360000

W 来自实测：6 次 prefill 前向 × 8 卡，每卡自身（非 MoE 部分）耗时 = 70 ms + 49.8 ms/千 token + 137 ms/十亿·上下文跨度，R² = 0.99；49.8 / 137 × 10⁶ ≈ 36 万。这个公式在 6 次里 6 次都选中了最慢的卡。

同样 k = 16384startcost
短上下文1 千≈ 60 亿
长上下文30 万≈ 110 亿（贵将近一倍）

3. 每个调度步做什么

改动全在 ATOM 调度器里。8 张卡的调度器每一步同时执行：

  1. 要不要做 prefill？原有

    PrefillDelayer 做一次 CPU all_reduce，8 卡一起决定。新加一个 8 卡一致的标志 any_rank_prefillable。

  2. 估算本卡这一步的代价新增

    _estimate_prefill_chunk_cost(16384)：按 16k 预算模拟排一遍批，先算做到一半的长 prompt，再算排队的新请求；新请求用 can_allocate(record=False) 只查前缀缓存命中、不真分配，得到 start。

  3. 交换代价新增

    gather_across_ranks()：每卡在长度 8 的向量里写自己那一格，在 DP 的 gloo 组上做一次 SUM all_reduce，8 卡都拿到全部代价。只在第 1 步放行且有卡要 prefill 时调用（8 卡结论一致），闲卡报 0 也参加，保证不会有卡缺席通信。

  4. 定目标新增

    target = min(最大代价, 有 prefill 的卡的平均代价 × 1.1)

  5. 按目标排批新增

    每个请求能分到的 token 数，从“剩余 token 预算”改成“剩余代价额度内能放下的最大 k”（_prefill_room()）；累计代价碰到目标就停。每步至少做 4096 个 token，最多 16k。

  6. 没做完的留到下一步原有

    请求停在“做了一半”的状态，下一步接着做（原有的 chunked prefill 机制，没改）。

第 5 步里“能放下的最大 k”就是解一元二次不等式：

k × (W + start + k/2) ≤ 剩余额度
⇒ k = √(a² + 2 × 剩余额度) − a        a = W + start

4. 例子：削完之后

5. 和“会话迁移（spill）”的区别

spill：挪会话本方案：削块
动什么会话放在哪张卡：某卡比最轻卡多 ≥20 万 token 时，把会话迁过去不动会话，只调这一步每卡 prefill 多少
时间尺度新一轮请求分配时每个 prefill 步
负载度量token 数注意力代价 k × (W + start + k/2)
额外开销从 LMCache 读回前缀；原卡前缀缓存浪费每步一次 CPU 小 all_reduce，不搬数据
结果−1.3%（另一台机，c256，900 s）+3.9% 吞吐，每用户速度 P90 +7.3%

不均衡是逐步突发的：每 10 秒窗口最重卡/平均卡的 prefill 量约 1.8 倍，但 30 分钟累计各卡几乎相等（0.89–1.13）。spill 只迁走了 6.6% 的轮次，不均衡没有变；削块直接压低每一步最慢那张卡。按 token 折算的负载均衡（lreq16k）只有 +0.8%，因为同样的 token 数代价可以差一倍。

放开到 32k 的坑

让轻卡长到 32k 时，PyTorch 缓存的空闲显存块在 2.5 分钟内比实际使用多出约 44 GB，把整卡塞满（287/287 GB）。之后共享这些卡的所有进程有 40–100% 的时间被换出，服务停住几分钟。给 PyTorch 缓存设上限（物理显存 − 非 PyTorch 占用 − 2% 余量）后，完整一小时无卡顿；但吞吐和 16k 版本持平，每用户速度 P90 反而回到基线，所以推荐 16k 只削不增。
